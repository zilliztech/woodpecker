Connection and naming

Follow CLI setup for a Helm-installed Milvus/Woodpecker deployment, including access from outside Kubernetes.

Name Meaning
logName / logId Logical metadata name / numeric log identity. Node-local logstore operations use the numeric ID.
meta-prefix Complete etcd namespace configured by the client, for example milvus-prod/woodpecker.
bucket + root-path The physical storage instance. Use both on scan, inspect and probe when automatic discovery cannot locate an empty or unloaded target. The instance data command uses --root.

Admin discovery supplies quorum identities; the workstation fans out to each node. Map every target to an accessible admin origin. A working seed connection alone does not establish peer reachability.

If the metadata namespace is unknown, start with Raw etcd exploration: list literal keys, narrow the prefix, then inspect a value. Those read-only operations need an etcd connection but no admin endpoint or metadata prefix.

For decoded records, metadata consistency and controlled correction, use Metadata inspection & repair. Normal retention advancement uses log truncate; it is separate from metadata patching and skip-range declarations.

Choose the intended change

Operation Intent / required preparation
meta log/segment patch Correct proven metadata errors using a JSON file containing only supported fields. Apply needs stopped writers/auditors, target revision, reason and a new backup.
log skip-range add Accept a precisely verified unreadable range when all usable alternatives fail. Requires explicit loss acceptance; it does not repair files or compaction.
log truncate Advance verified application retention. Apply needs the log revision, reason and a new backup; later auditor rounds retire earlier finalized segments.

Preview success does not commit a change. Metadata patch/truncate previews normally exit 0; skip-range and fencing previews can exit 7 because acceptance was not given. Verify application recovery independently after any intervention.

Output formats vary by operation. Profile downloads binary data, and some diagnostic operations return findings with a nonzero exit code. Read the specific command's help and interpretation rather than treating every successful request as a health check.

Metrics scenario limits

stuck-read and stuck-write require persistent matching operations as well as zero successful completion progress during the window. An idle cluster alone is not a stall. Latency rules currently use window-average histogram latency rather than the advertised p99/baseline model. Several scenario names have only partial evaluators; use counters, operation IDs, reader positions and replica evidence together. A scenario reporting no findings is not proof that the whole cluster is healthy.

Exit codes and expected findings

Code Meaning
0 Completed within the command's stated scope.
1 / 2 / 3 / 4 Network / usage / target absent / state conflict.
5 / 6 / 7 Wait timeout / strict partial failure / acceptance not given or aborted.
8 / 9 Yellow / red diagnostic finding.
10 / 11 / 12 / 13 Not implemented / resource absent / configuration / prerequisite error.
100 + N Executed kubectl exit code N.

Read the exit status immediately with echo $?. Piping through another command can hide the original status unless pipefail is enabled. Example output throughout the handbook is illustrative and may omit fields; replace names and IDs with values from your own cluster.

CLI Handbook overview / CLI setup

CLI setup

Configure wp and run your first commands from outside Kubernetes.

0. Install wp

Assume Milvus with Woodpecker is already installed by Helm. Run wp on your workstation using a released binary or a source build. The shell examples below use bash/zsh on macOS or Linux.

Download from GitHub

Select the release and OS/CPU architecture on the GitHub Releases page. These are standalone binaries, not archives. For example, macOS on Apple Silicon:

Example / output
export WP_VERSION=v0.1.47
mkdir -p "$HOME/.local/bin"
curl -fL "https://github.com/zilliztech/woodpecker/releases/download/${WP_VERSION}/wp-darwin-arm64" \
  -o "$HOME/.local/bin/wp"
chmod +x "$HOME/.local/bin/wp"
export PATH="$HOME/.local/bin:$PATH"
wp version

For Linux, use wp-linux-amd64 or wp-linux-arm64; Windows uses wp-windows-amd64.exe. Use an available asset matching your machine.

Alternative: build from source
Example / output
git clone https://github.com/zilliztech/woodpecker.git
cd woodpecker
# Optionally check out the release/branch you want to build.
# git checkout v0.1.47
make wpcli
mkdir -p "$HOME/.local/bin"
cp bin/wp "$HOME/.local/bin/wp"
export PATH="$HOME/.local/bin:$PATH"
wp version

Install Git, make and the Go version required by go.mod first. You may also run ./bin/wp directly. A source build exposes the commands in that checkout; a released binary may not contain later development additions documented in this handbook. Check wp --help.

1. Connect to the Helm deployment

Use your real kubeconfig and namespace. Find the Woodpecker and etcd pods:

Example / output
export KUBECONFIG=/path/to/your/kubeconfig
kubectl -n milvus get pods -o wide

The examples below assume namespace milvus, Woodpecker pods milvus-woodpecker-0/1/2 and etcd pod milvus-etcd-0. Replace these names with the Helm deployment's actual names. Start each needed forward in its own terminal:

Example / output
kubectl -n milvus port-forward pod/milvus-woodpecker-0 19091:9091
kubectl -n milvus port-forward pod/milvus-woodpecker-1 29091:9091
kubectl -n milvus port-forward pod/milvus-woodpecker-2 39091:9091
# Needed when querying coordinator metadata or raw etcd keys:
kubectl -n milvus port-forward pod/milvus-etcd-0 32379:2379

The seed discovers membership; it does not proxy other nodes. Inspect the advertised node IDs/addresses, then map every node you need to reach:

Example / output
wp cluster info --endpoint http://127.0.0.1:19091

2. Save the connection in cli.yaml

The usual personal location is ~/.woodpecker/cli.yaml. Create the directory and save this example YAML there, using the node IDs reported by your cluster:

Example / output
mkdir -p "$HOME/.woodpecker"
Example / output
current-context: milvus-prod
contexts:
  milvus-prod:
    endpoint: http://127.0.0.1:19091
    node_admin_urls:
      milvus-woodpecker-0: http://127.0.0.1:19091
      milvus-woodpecker-1: http://127.0.0.1:29091
      milvus-woodpecker-2: http://127.0.0.1:39091
    k8s:
      namespace: milvus
      kubeconfig: /path/to/your/kubeconfig
    # v0.1.47 and later; v0.1.46 uses explicit etcd flags instead.
    etcd:
      endpoints:
        - 127.0.0.1:32379
      meta_prefix: milvus-prod/woodpecker

endpoint is the admin seed. node_admin_urls maps discovered node IDs or advertised service addresses to reachable admin origins. current-context selects milvus-prod when --context is omitted:

Example / output
wp node list
wp --context milvus-prod node list

To keep cli.yaml in another directory, select it explicitly:

Example / output
export WOODPECKER_CLI_CONFIG=/path/to/your/cli.yaml
wp ctx list
wp --context milvus-prod ctx view
Config locations and precedence

Search order: WOODPECKER_CLI_CONFIG → cli.yaml beside the resolved wp binary → $XDG_CONFIG_HOME/woodpecker/cli.yaml → ~/.woodpecker/cli.yaml. The working directory and /etc/woodpecker are not default locations. Explicit command flags override matching context fields. WOODPECKER_ENDPOINT overrides the context's endpoint unless --endpoint is given.

The k8s block supplies defaults to wp k8s helpers, not to your shell's kubectl. Operator-specific helpers target a WoodpeckerCluster CR; for a Helm deployment without that CR, use kubectl directly. Do not use the Helm release name as k8s.cluster unless it is also the actual CR name.

3. Run without cli.yaml, or add shortcuts

A config file is optional. Supply the admin endpoint and node mappings directly:

Example / output
wp node list --endpoint http://127.0.0.1:19091 \
  --node-admin-url milvus-woodpecker-0=http://127.0.0.1:19091 \
  --node-admin-url milvus-woodpecker-1=http://127.0.0.1:29091 \
  --node-admin-url milvus-woodpecker-2=http://127.0.0.1:39091

Replace node IDs with the discovered IDs, full advertised addresses or hostnames. Repeat --node-admin-url for each peer; --endpoint alone only makes the seed reachable. CLI flags can also override an existing cli.yaml for one invocation.

Optional: source shell functions for shorter commands

After creating the milvus-prod context, save this as a file of your choice, for example ~/wp-env.sh:

Example / output
export KUBECONFIG=/path/to/your/kubeconfig
# Set this only when cli.yaml is outside the usual personal location:
# export WOODPECKER_CLI_CONFIG=/path/to/your/cli.yaml

k() { kubectl --kubeconfig "$KUBECONFIG" -n milvus "$@"; }
w() { wp --context milvus-prod "$@"; }
Example / output
source ~/wp-env.sh
k get pods
w node list
w cluster health

source defines the functions in the current shell. w forwards arguments to wp and selects milvus-prod for each invocation; it does not change current-context in the file.

4. Configure etcd for metadata queries

Released v0.1.47 supports the context's etcd block shown above. Set reachable endpoints and the complete metadata prefix, then run wp --context milvus-prod log readers my-channel without repeating those flags. Explicit etcd flags override the matching context fields. Metadata commands can discover missing endpoints/prefix through a reachable node's admin config; discovered in-cluster addresses or certificate paths may not work on a workstation, so set local equivalents.

Released v0.1.46 does not read etcd connection settings from cli.yaml. See the released config schema. Use the explicit flags below on that release, or to override a context for one invocation:

Parameters Use
--etcd Reachable etcd endpoints; use commas for multiple addresses.
--meta-prefix Complete Woodpecker metadata prefix configured by the Milvus client. The example below uses milvus-prod/woodpecker; use the actual prefix, not an assumed Helm release name.
--etcd-username / --etcd-password Etcd authentication credentials when required.
--etcd-cacert CA certificate file on the workstation.
--etcd-cert / --etcd-key Workstation client certificate and private-key files.
--etcd-tls-min-version Minimum TLS version: 1.0, 1.1, 1.2 or 1.3.

For example, inspect registrations for a real Milvus log name using explicit connection settings:

Example / output
wp log readers my-channel \
  --etcd 127.0.0.1:32379 \
  --meta-prefix milvus-prod/woodpecker
Commands Need etcd settings?
meta; log readers/scan/skip-range/truncate; segment probe/inspect; logstore lac/fence-quorum; marking list/confirm Yes: they look up log/segment/quorum or operational metadata. Supply endpoint and complete prefix through context, flags or admin discovery. meta and truncate need no admin connection when both etcd settings are supplied.
etcd list/get/cat (v0.1.47 and later) Etcd endpoints and any required TLS/auth settings only. No admin discovery or metadata prefix: keys/prefixes are literal. See Raw etcd exploration.
cluster, node, config, env, logging, profile, ops, metrics, instance; other node-local logstore commands No etcd parameters: these use node admin endpoints. Do not append --etcd to commands that do not accept it.
ctx, completion, version; k8s helpers No etcd connection. These use local config/build information or kubectl.
Authentication/TLS example
Example / output
wp log readers my-channel \
  --etcd etcd.example.com:2379 --meta-prefix milvus-prod/woodpecker \
  --etcd-username operator --etcd-password 'YOUR_PASSWORD' \
  --etcd-cacert /path/to/ca.crt \
  --etcd-cert /path/to/client.crt --etcd-key /path/to/client.key \
  --etcd-tls-min-version 1.2

Certificate paths must exist on the workstation; paths returned by a server may be in-container paths. v0.1.47 also supports these optional context fields under etcd:

Example / output
username: operator
password: YOUR_PASSWORD
tls_enabled: true
cacert: /path/to/ca.crt
# cert/key are a pair, required only for mutual TLS:
cert: /path/to/client.crt
key: /path/to/client.key
tls_min_version: "1.2"

Use a CA alone for server-authenticated TLS, or tls_enabled: true with system trust roots. Supplying cert/key enables mutual TLS; they must be supplied together. The current source default minimum TLS version is 1.2. Explicit certificate flags enable TLS even if the context disables it. ctx view shows configured etcd endpoints, prefix, TLS mode and username when endpoints are configured; it does not print the password or test the connection.

Interactive service and tenant sessions

Source builds that include wp shell can retain a service context and an independent tenant metadata connection. Without --context, the shell always lists configured contexts in alphabetical order, marks a valid saved current context as the Enter default, and accepts a number or exact name. An explicit wp shell --context milvus-prod skips selection. The choice is session-local and does not rewrite cli.yaml.

Example / output
wp shell
# Choose a context by number or name, then omit the leading wp:
node list
cluster health
connect tenant-a --etcd 127.0.0.1:32379 --meta-prefix tenant-a/woodpecker --bucket tenant-a-bucket --root-path milvus/wp
meta log list
log readers application-log
log scan application-log --mode raw
segment inspect application-log 0
status
status --check
connect tenant-b --etcd 127.0.0.1:42379 --meta-prefix tenant-b/woodpecker
disconnect
use wp-staging
exit

The prompt identifies both configured targets: wp[context=milvus-prod | meta=tenant-a]>. Entry always starts with meta=disconnected, even if the service context stores etcd settings. Metadata commands require an explicit attachment. connect validates a bounded etcd read, accepts the existing etcd authentication/TLS options, and replaces all tenant settings only after validation succeeds. Failed connections retain the previous target. The full metadata prefix and the storage root are distinct settings.

A metadata-only attachment can omit both storage options. Physical inspection (log scan, segment inspect, segment probe) requires an explicit bucket/root pair from the attachment or command flags before making requests. Command overrides do not change session defaults. disconnect clears all tenant settings; a successful use also detaches the tenant. Session-local use is distinct from persistent ctx use.

status shows effective settings and the original configuration source without requests, and redacts credentials. status --check explicitly checks Admin and etcd separately. The prompt is a target indicator, not a live health check. The shell uses the selected service context rather than a baked-in WOODPECKER_ENDPOINT; standalone CLI endpoint precedence is unchanged.

Tab completes commands and flags; arrow keys recall in-memory session history. Connection and credential-bearing lines are excluded, and no history file is written. Ctrl+C cancels an operation while retaining the session; existing mutation confirmations, previews and backup/revision requirements remain mandatory. Each operation runs in an isolated wp process with a private temporary configuration, removed afterward, so options such as --apply and --yes cannot leak to later commands. Use status to identify the original source when a child diagnostic names a temporary configuration.

Piped input requires an explicit context and exits nonzero if any command fails: printf 'status\nnode list\nexit\n' | wp shell --context milvus-prod. Ordinary CLI calls remain available for scripts. For a complete configuration example and multi-tenant walkthrough, see the interactive shell guide.

Metadata inspection & repair

Read decoded coordinator records, check metadata constraints, export snapshots and apply reviewed corrections.

1. Read the record before choosing a repair

Use a current source build containing wp meta and wp log truncate; these additions are not in v0.1.46. Complete CLI setup first. The commands below assume the milvus-prod context has reachable etcd endpoints and the complete metadata prefix. With both configured, no node admin connection or bucket/root-path is needed.

Example / output
wp --context milvus-prod meta log list
wp --context milvus-prod meta log show my-channel
wp --context milvus-prod meta segment list my-channel
wp --context milvus-prod meta segment show my-channel 7
wp --context milvus-prod meta check my-channel

Use the real logical log name. list includes persisted history even when node-local writer objects are unloaded. show wraps decoded metadata with its exact key, modification revision and lease; int64 fields appear as decimal strings. For modern segments, inspect the embedded quorum in segment show; separately stored quorum records may be absent.

2. Create a small JSON patch file

Pass only fields to change, not the show envelope or a full exported record. For example, create the files used by the command demos below:

Example / output
cat > ./log-policy.json <<'JSON'
{"max_segment_roll_time_seconds": 120}
JSON

# Only after independently proving that 99 is the correct finalized tail:
cat > ./segment-repair.json <<'JSON'
{"lastEntryId": "99"}
JSON
Patch target Writable fields / constraints
log max_segment_roll_time_seconds, max_segment_roll_size_bytes, compaction_buffer_size_bytes, max_compaction_file_count. Nonnegative; zero is allowed. These are reserved metadata fields, not live client runtime configuration.
segment size, createTime, completionTime, sealedTime, lastEntryId, state. Times are Unix milliseconds; size is bytes. Lifecycle times must agree with state. Integers may be numbers or decimal strings.
Protected Identity (logId/segNo), quorum and log truncation fields. Quorums are read-only; advance normal retention with log truncate.

Active requires lastEntryId=-1 and zero completion/sealed times. A verified rollback to Active must reset all three together. Completed/Sealed lastEntryId=-1 means finalized empty; Sealed needs a valid sealedTime. A key/segNo mismatch is rejected. Changing state does not generate compacted objects, repair data or execute recovery; Truncated can enable cleanup.

State-correction JSON examples

Use only the state independently verified for this segment. These are alternative patch-file contents, not automatic recovery steps. For a verified rollback to Active:

Example / output
{"state":"Active","lastEntryId":"-1","completionTime":"0","sealedTime":"0"}

For a verified Completed-to-Sealed correction with existing compacted files and a known sealing time:

Example / output
{"state":"Sealed","lastEntryId":"99","sealedTime":"1791806000000"}

The timestamp is illustrative: replace it with the verified Unix-millisecond value, after completionTime. State names are Active, Completed, Sealed and Truncated (numbers 0, 2, 3, 4); reserved state 1 is rejected. A legacy createTime=0 must also be corrected with a verified positive creation time.

3. Preview, stop metadata writers, then apply

Example / output
wp --context milvus-prod meta segment patch my-channel 7 \
  --patch-file ./segment-repair.json

A preview returns applied=false, before/after records, changes and snapshot_revision. Review all changes. Use the target's before.revision for apply. If it is 174, stop the relevant writers/auditors and keep them stopped throughout the repair:

Example / output
wp --context milvus-prod meta segment patch my-channel 7 \
  --patch-file ./segment-repair.json --apply --offline \
  --expected-revision 174 --reason 'Correct verified tail after software fix' \
  --backup ./segment-before-repair.json

wp --context milvus-prod meta segment show my-channel 7
wp --context milvus-prod meta check my-channel

--offline acknowledges your action; it does not stop clients. Apply checks revision and writer-lock absence, persists a new backup, and writes the correction and audit record atomically. Restart affected clients after repair so cached metadata is refreshed. applied=true/new_revision confirms the write, not data readability. Reused backup paths fail; stale revisions or concurrent changes require a fresh preview and a new backup filename.

Example / output
# Example warning on an otherwise valid scalar repair:
"warnings": [
  "embedded quorum (unchanged): invalid quorum sizes or node count"
]

An existing embedded-quorum problem is preserved and reported in warnings; it does not block an independent scalar repair. meta check still reports that unresolved problem. Lifecycle and truncation-bound violations continue to block the patch. Do not mark a segment Sealed or lower a tail just to silence a physical corruption finding.

4. Interpret checks, exports and failures

Result Meaning / next step
check: state=ok, issues=[]; exit 0 The inspected metadata constraints passed. Probe/inspect separately for physical data; verify application progress separately.
check: state=invalid; exit 9 Read the exact key/field in issues. A bad frontier, lifecycle or quorum is metadata evidence, not automatic permission to rewrite it.
TargetNotFound; exit 3 The exact record is absent. Verify context, prefix and logical IDs before diagnosing missing payloads.
Patch StateConflict; exit 4 Read the constraint, revision or writer-lock error. Re-read records and correct the verified cause; do not blindly retry apply.
export / backup New mode-0600 file with readable known metadata and original value_base64/revisions/leases. File and parent directory must sync before patch commits. Unknown/malformed records retain their bytes. This is not a payload backup or automatic rollback command.

If commit returns a network error, re-read the target and audit records before retrying: the write outcome may be unknown. For a complete operational example, follow verified metadata repair in Troubleshooting.

Raw etcd exploration

Discover namespaces and inspect exact raw keys, revisions and values without writing etcd.

1. Discover keys before choosing a metadata prefix

This command group is included in v0.1.47 and later; it is not included in v0.1.46. Install a matching release or build from source, and confirm wp etcd --help before using these examples.

Use this read-only group when you can reach etcd but do not yet know the Woodpecker namespace. It connects directly to etcd: no Woodpecker admin endpoint, node mapping or metadata prefix is required. Supply a reachable endpoint, or save it in a context as shown below.

Example / output
# Omit the prefix to explore all keys (first page only).
wp etcd list --etcd 127.0.0.1:32379 --limit 20
# Narrow the listing using an actual prefix found in that output.
wp etcd list milvus-prod/ --etcd 127.0.0.1:32379 --limit 20

Illustrative excerpt:

Example / output
KEY                              MOD_REV  VERSION  LEASE
milvus-prod/woodpecker/version    90       1        0

1 keys shown; snapshot revision 105; more=false

A prefix is literal: list / lists only keys starting with a slash; it does not mean all keys. Empty results mean no matching keys in this snapshot, not an unhealthy cluster. A connection or permission error means the listing could not be established. This group never prepends the context's etcd.meta_prefix.

2. Inspect a key and understand its value

Example / output
wp etcd get milvus-prod/woodpecker/version --etcd 127.0.0.1:32379 -o json
wp etcd cat milvus-prod/woodpecker/version --etcd 127.0.0.1:32379 --encoding base64
Operation / option What you get
get; -o json / -o yaml Exact key, key revision, lease, snapshot revision, encoding and value. Default get output is JSON.
cat The value alone. It is useful for piping or saving a single value.
--encoding auto Readable UTF-8 text is printed as text; binary/control-byte content becomes base64. get reports the selected value_encoding; cat prints a base64 notice on stderr.
--encoding text / base64 / hex Choose the representation explicitly. text rejects invalid UTF-8. Protobuf bytes do not become decoded metadata simply by selecting text.
cat --encoding raw Exact original bytes, without an appended newline. Redirect to a file rather than displaying binary content in a terminal.
Example / output
wp etcd cat milvus-prod/woodpecker/version \
  --etcd 127.0.0.1:32379 --encoding raw > /tmp/wp-version.pb

A TargetNotFound result means that exact key is absent at the requested snapshot. Base64 is a reversible byte representation, not evidence of damaged data. This raw group does not decode, patch or restore metadata; the file above preserves one value, not a complete etcd backup.

Once you know the Woodpecker prefix, use Metadata inspection & repair for decoded log/segment records and readable namespace exports. Supply that complete prefix through context or --meta-prefix.

3. Continue a listing at the same snapshot

Use JSON output for pagination. When more is true, copy next_key_base64 and snapshot_revision from that response into the next request, keeping the same prefix:

Example / output
wp etcd list milvus-prod/ --etcd 127.0.0.1:32379 --limit 20 -o json

# Replace these placeholders with the returned cursor and snapshot revision.
wp etcd list milvus-prod/ --etcd 127.0.0.1:32379 --limit 20 -o json \
  --after-key-base64 'CURSOR_FROM_PREVIOUS_RESPONSE' --revision 105

Repeat until more=false. The base64 cursor preserves binary keys. The keys array contains this page; count describes matching keys remaining in the queried range, so it can exceed the page length. --after-key is an alternative for ordinary text keys; never combine it with --after-key-base64.

Use --revision on get/cat too when comparing values with a listing. If etcd has compacted that revision, restart the listing at a new snapshot; do not silently mix pages from different revisions.

5. Close the compaction/retention loop

Reader recovery and compaction are separate. Skip-range does not fix a damaged Completed copy. Later eligible segments can be compacted independently; the damaged segment may continue failing until repaired or deliberately retired.

After verifying resumed application progress and a durable checkpoint beyond the damaged segment, advance normal retention with log truncate. The example assumes segment 8 is non-empty Completed/Sealed and its entry 0 is a verified safe boundary. Advancing into 8 permits retiring segment 7; truncating to 7:99 retains segment 7 itself.

Example / output
wm meta segment show "$WP_LOG" 8

The preview has applied=false, unchanged=false, before/after and target_segment_revision. Use the log before.revision for apply (17099 in this illustrative example), not the target segment revision. No --offline flag is needed for this normal retention operation; coordinate it with the application's checkpoint policy.

Example / output

  --apply --expected-revision 17099 \
  --reason 'Verified durable application checkpoint beyond damaged segment 7' \
  --backup ./log-before-truncate.json
wm meta log show "$WP_LOG"

applied=true/new_revision confirms the frontier update and audit record, not immediate deletion. An unchanged frontier returns unchanged=true/applied=false with no new artifacts. Active/empty targets, backward movement, bad identity, missing apply guards and stale/concurrent revisions are rejected; inspect the message and preview again rather than forcing a change.

A live application log handle/auditor marks earlier finalized segments Truncated in subsequent rounds, then applies retention and reader protection. Welcome to Woodpecker

A cloud-native Write-Ahead Log storage engine that leverages object storage for low-cost, high-throughput, and reliable logging.

What is Woodpecker?

Woodpecker is a cloud-native WAL (Write-Ahead Log) storage implementation designed to fully utilize cloud-native infrastructure for scalability and durability. Unlike traditional on-premises WAL solutions or custom-built distributed logging systems, Woodpecker uses cloud object storage as its durable storage layer.

Woodpecker is currently under active development. Initially built for Milvus vector database and Zilliz Cloud, with broad applicability across cloud workloads.

Key Features

  • Cloud-Native WAL — Uses cloud object storage (S3, GCS, Azure, OSS) as the durable layer for scalability and cost-effectiveness
  • High-Throughput Writes — Optimized write strategies achieving 60-80% of maximum backend throughput
  • Efficient Log Reads — Memory management and prefetching strategies for optimized sequential access
  • Ordered Durability — Strict sequential ordering guarantees for log persistence
  • Flexible Deployment — Standalone service mode or embedded library mode
  • Multi-Cloud Support — AWS, GCP, Azure, Aliyun, Tencent Cloud, MinIO
  • Innovative Quorum Protocol — Configurable ensemble/write/ack quorum with AZ-aware placement
  • Condition Write Fence — Prevents split-brain with built-in fence mechanism

Design Benefits

  • Lightweight deployment — Easy integration with minimal dependencies
  • Decoupled compute & storage — Reduced operational complexity
  • Auto-scaling storage — Eliminates capacity planning overhead
  • Reduced local disk dependency — Ideal for cloud-native workloads
  • One-write, multiple-reads — Data-embedded metadata design enables concurrent reads without writer synchronization

func main() {
	file := flag.String("config", "client.yaml", "SDK configuration file (not wp CLI cli.yaml)")
	flag.Parse()
	if err := run(*file); err != nil {
		log.Fatal(err)
	}

func run(file string) error {
	ctx, cancel := context.WithTimeout(context.Background(), 90*time.Second)
	defer cancel()
	cfg, err := config.NewConfiguration(file)
	if err != nil {
		return fmt.Errorf("load SDK configuration: %w", err)
	}

	var client woodpecker.Client
	if cfg.Woodpecker.Storage.IsStorageService() {
		etcdClient, err := clientv3.New(clientv3.Config{
			Endpoints:   cfg.Etcd.GetEndpoints(),
			DialTimeout: 5 * time.Second,
		})
		if err != nil {
			return fmt.Errorf("create etcd client: %w", err)
		}
		defer etcdClient.Close()
		client, err = woodpecker.NewClient(ctx, cfg, etcdClient, false)
		if err != nil {
			return fmt.Errorf("create service client: %w", err)
		}
	} else if cfg.Woodpecker.Storage.IsStorageMinio() {
		client, err = woodpecker.NewEmbedClientFromConfig(ctx, cfg)
		if err != nil {
			return fmt.Errorf("create embedded client: %w", err)
		}
	} else {
		return fmt.Errorf("this example supports storage.type service or minio")
	}
	defer client.Close(context.Background())

	name := fmt.Sprintf("quickstart-%d", time.Now().UnixNano())
	if err := client.CreateLog(ctx, name); err != nil {
		return fmt.Errorf("create log: %w", err)
	}
	handle, err := client.OpenLog(ctx, name)
	if err != nil {
		return fmt.Errorf("open log: %w", err)
	}
	defer handle.Close(context.Background())
	writer, err := handle.OpenLogWriter(ctx)
	if err != nil {
		return fmt.Errorf("open writer: %w", err)
	}
	defer writer.Close(context.Background())

	payload := []byte("hello, Woodpecker")
	result := writer.Write(ctx, &wplog.WriteMessage{Payload: payload})
	if result.Err != nil {
		return fmt.Errorf("write: %w", result.Err)
	}
	fmt.Printf("WROTE log=%s position=%d:%d\n", name, result.LogMessageId.SegmentId, result.LogMessageId.EntryId)

	reader, err := handle.OpenLogReader(ctx, result.LogMessageId, "quickstart")
	if err != nil {
		return fmt.Errorf("open reader: %w", err)
	}
	defer reader.Close(context.Background())
	message, err := reader.ReadNext(ctx)
	if err != nil {
		return fmt.Errorf("read: %w", err)
	}
	if !bytes.Equal(message.Payload, payload) || *message.Id != *result.LogMessageId {
		return fmt.Errorf("read result differs from acknowledged write")
	}
	fmt.Printf("READ position=%d:%d payload=%q\n", message.Id.SegmentId, message.Id.EntryId, message.Payload)
	fmt.Printf("VERIFIED mode=%s messages=1\n", cfg.Woodpecker.Storage.Type)
	return nil
}

System Architecture

Understanding Woodpecker's two deployment modes and core design.

Embedded Mode

In embedded mode, Woodpecker operates as a lightweight library integrated directly into your application. It requires only etcd for metadata storage and coordination, keeping dependencies minimal.

Key characteristics of embedded mode:

  • Zero additional services required beyond etcd
  • Client directly writes to object storage
  • Condition-write fence mechanism prevents split-brain
  • Best suited for applications needing simple WAL integration

Service Mode

In service mode, WAL read/write operations and caching logic are decoupled into a dedicated LogStore cluster service. This acts as a high-performance caching layer between clients and object storage.

Key characteristics of service mode:

  • Dedicated LogStore cluster with gRPC communication
  • Data prefetching and read/write caching for lower latency
  • Gossip-based cluster membership and auto-discovery
  • Quorum-based replication with AZ-aware node placement
  • Best suited for high-throughput, latency-sensitive workloads

Core Components

ClientRead/write protocol layer connecting applications to Woodpecker
EmbeddedClientCombined client + LogStore for embedded deployments
LogStoreHigh-speed log writes, batching, caching, and cloud storage uploads
ObjectStorageDurable storage backend using S3-compatible APIs

Data Flow

Write Path

  1. Application calls Write() or WriteAsync() on a LogWriter
  2. Writer validates the session lock is still valid (distributed lock via etcd)
  3. Gets or creates a writable segment via rolling policy (maxSize=100MB, maxInterval=800s, maxBlocks=1000)
  4. Serializes message with MarshalMessage() (payload + properties)
  5. Calls segment.AppendAsync() — data is buffered
  6. Buffer is flushed to storage when sync policy triggers (maxInterval=1000ms, maxEntries=2000, maxBytes=100MB)
  7. Segment metadata updated in etcd with revision-based optimistic locking

Read Path

  1. Application opens a LogReader with starting position and reader name (OpenLogReader(ctx, from, readerName))
  2. Reader loads entries in batches via ReadBatchAdv() (batch limit: 200 entries)
  3. Yields one entry per ReadNext() call from local cache
  4. On segment EOF, auto-advances to the next segment seamlessly
  5. Reader position updated in etcd every 30 seconds
  6. For active (still-writing) segments, polls with 200ms wait interval when no new data is available

Segment Lifecycle

Segments transition through the following states:

State Machine
Active → Completed → Sealed → Truncated → (Deleted)

Active     - Currently accepting writes
Completed  - All data flushed, no more writes
Sealed     - Metadata finalized, immutable
Truncated  - Marked for cleanup
Deleted    - Storage data removed

Quorum Protocol

Woodpecker's innovative quorum-based replication for service mode deployments.

Overview

In service mode, Woodpecker uses a configurable quorum protocol for data replication across LogStore nodes. This ensures data durability while allowing flexible tradeoffs between consistency, availability, and performance.

Quorum Parameters

The quorum is configured via the replicas setting, which determines the ensemble size (E). Write quorum (WQ) and ack quorum (AQ) are derived automatically:

ParameterSymbolFormulaE=3E=5
Ensemble SizeE= replicas35
Write QuorumWQ= E35
Ack QuorumAQ= (E / 2) + 123
Data is written to all E nodes (WQ = E), but only AQ acknowledgments are required before the write is considered durable. This allows writes to succeed even if some nodes are slow, while ensuring majority-based durability.

Buffer Pools

Buffer pools are logical groupings of LogStore nodes. Each pool is defined by a name and seed addresses used for gossip-based node discovery. Pools enable regional grouping of nodes for locality-aware placement.

Service mode uses HashiCorp memberlist (gossip protocol) for cluster membership management:

  • Nodes discover each other via seed addresses configured in buffer pools
  • Health status is propagated through gossip protocol
  • Failed nodes are automatically detected and excluded from quorum selection
  • New nodes can join the cluster dynamically by connecting to any seed
  • Each node exposes a bind port (gossip) and a service port (gRPC)

Condition write (PutObjectIfNoneMatch) is used as a fence mechanism to prevent split-brain in embedded mode. It ensures only one writer can create a given object key.

  • AWS/MinIO/GCS/Azure — Uses If-None-Match: * header for conditional PUT
  • Aliyun OSS / Tencent COS — Uses the forbid-overwrite feature (wrapped implementation)
  • Auto-detection — Woodpecker probes condition write support at startup (configurable via fencePolicy.conditionWrite)

Performance Best Practices

Write Optimization

  • The default maxFlushSize is 16MB — increase for larger batch uploads to reduce API call overhead
  • Default maxFlushThreads is 8 — increase for higher parallelism on fast networks
  • Use WriteAsync with batching for maximum throughput
  • Compaction merges small blocks into 32MB merged blocks (configurable via segmentCompactionPolicy.maxBytes)

Read Optimization

  • Read batch size is 16MB by default (segmentReadPolicy.maxBatchSize)
  • Up to 32 concurrent fetch threads for parallel reads (segmentReadPolicy.maxFetchThreads)
  • Range reads via GetObject with offset/size parameters for partial fetches

Data Durability

  • CRC32 checksums for data integrity verification on every block
  • Automatic retry on transient failures with configurable backoff (up to maxFlushRetries = 3, interval = 2s)
  • Fragment-based storage for incremental durability — data is durable as soon as each block is flushed
  • Segment compaction merges small fragments into larger objects for efficient storage and reads

Local File System Storage

High-performance disk-based log storage using memory-mapped I/O.

Overview

The local file system storage implements disk-based log storage using mmap (memory mapping) for efficient read and write performance. It maintains the Fragment concept for consistency with the object storage implementation.

Key Design Decisions

Why mmap?

  • Zero-copy read/write operations
  • Random access support
  • OS-managed page caching
  • Memory-level read/write performance

Why Fragments?

Although the local file system supports append operations, maintaining fragments provides:

  • Architecture consistency with object storage backend
  • File size limitation support
  • Segmented management and cleanup
  • Simplified concurrency control
  • Better system recovery capability

  • File locks to prevent concurrent writes

Staged Storage (Service Mode)

Two-tier hybrid storage combining local disk speed with object storage durability for service mode deployments.

Overview

Staged storage is the storage backend used in service mode (storage.type: service). It implements a two-tier hybrid architecture: active segments write to local disk for low-latency writes, then compaction uploads merged blocks to object storage for durable, long-term persistence.

Staged storage is automatically used when storage.type is set to service. No additional configuration is needed beyond configuring the MinIO/S3 backend for the object storage tier.

How It Works

Data Flow
Write Path:
  Client → LogStore Server → Local Disk (fast, low-latency)

Compaction:
  Local Disk → Merge Blocks → Object Storage (durable)

Read Path:
  Active segments  → Read from Local Disk
  Compacted data   → Read from Object Storage

Core Components

ComponentRole
StagedSegmentImplManages a segment's lifecycle across both tiers — coordinates writes to local disk and compaction uploads to object storage
StagedFileWriterHandles buffered writes to local disk files with block-based batching and CRC32 integrity checks
StagedFileReaderAdvReads entries from either local disk (active segments) or object storage (compacted segments) transparently

Configuration

Enable staged storage by setting storage.type: service:

woodpecker.yaml
woodpecker:
  storage:
    type: service              # enables staged storage
    rootPath: /var/lib/woodpecker # local staging directory

# Object storage tier (for compacted data)
minio:
  address: localhost
  port: 9000
  accessKeyID: minioadmin
  secretAccessKey: minioadmin
  bucketName: a-bucket
  rootPath: files

Benefits

  • Low write latency — Writes go to local disk first, avoiding object storage API overhead
  • High durability — Compaction ensures all data reaches object storage for long-term persistence
  • Efficient reads — Active data served from local disk; compacted data served from object storage with prefetching
  • Automatic lifecycle — Compaction runs automatically based on configured policies
  • Reduced API costs — Merging blocks before upload reduces the number of object storage API calls

Condition Write & Fence

Split-brain prevention using condition write as a fence mechanism.

Overview

In embedded mode, Woodpecker uses condition write as a fence mechanism to prevent split-brain scenarios where a stale primary node resumes writing after being partitioned or crashed. This ensures data consistency and prevents concurrent write conflicts.

Supported Storage Backends

BackendSupportMechanism
MinIOFullIf-None-Match header
AWS S3FullConditional PUT operations
Azure BlobFullConditional writes
GCP Cloud StorageFullConditional operations
Aliyun OSSWrappedForbid overwrite feature
Tencent COSWrappedForbid overwrite feature

Detection Modes

Auto Mode (Default)

Follows existing true/false cluster metadata when present. If no metadata exists, verifies condition write support with strict enable semantics, stores true on success, and fails startup on failure.

Verification failure is surfaced immediately and is never persisted as an unsupported capability.

Enable Mode

Strict requirement: stored true is trusted, stored false is ignored, verification must succeed within 10 retries, and successful verification overwrites metadata to true.

Disable Mode

Skips detection entirely and uses distributed locks. Use when you know your backend doesn't support condition write.

Distributed Lock Fallback

When condition write is explicitly disabled, or when legacy auto metadata stores false, Woodpecker uses etcd-based distributed locks:

PropertyDetail
Lock Typeetcd concurrency.Mutex with concurrency.Session
Session TTL10 seconds (auto-renewed via keep-alive)
Lock Key/woodpecker/service/lock/{logName}
AcquisitionNon-blocking TryLock

Failover Behavior

  1. Session Expiration — etcd session expires after TTL (10s) if keep-alive fails
  2. Lock Release — Distributed lock is automatically released
  3. New Primary — New node acquires the lock
  4. Writer Switch — Applications reopen writer (up to 10s wait)
