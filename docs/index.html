01 / THE FOUNDATION

The log is fundamental.
Its infrastructure can be simpler.

Separate the WAL from your application. Use replication for the active write path and object storage for compacted segments.

≋

Replicated by design

Configurable ensemble, write and acknowledgement quorums, with placement controls for availability zones and resource groups.

Understand the quorum ↗
▱

Storage that goes further

Stage active writes on LogStore nodes. Compact completed segments into object storage, separating compute from long-term retention.

Follow the storage lifecycle ↗
⌁

Built to be operated

Inspect runtime health, trace slow operations and diagnose replica data with the wp CLI and documented recovery workflows.

02 / ONE ENGINE, TWO WAYS TO RUN

Your architecture.
Your deployment.

Choose a dedicated LogStore service or an in-process library. Both use etcd for coordination and share the Woodpecker log API.

DEDICATED CLUSTER

Service mode

Move WAL processing into a replicated LogStore cluster. Manage log storage independently from application compute.

APPLICATION→LOGSTORE × N→OBJECT
STORAGE
  • Quorum-based replication and node selection
  • Local staging with object-storage compaction
  • Cluster diagnostics and operational tooling
Deploy a service ↗
IN-PROCESS LIBRARY

Embedded mode

Run the log engine inside your Go application. Use the object-storage backend without a separate LogStore cluster.

APPLICATION
+ WOODPECKER→OBJECT STORAGE
  • Go library integration
  • No dedicated LogStore service to deploy
  • Etcd and storage backends configured by the application
Integrate the library ↗
