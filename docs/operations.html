Operations Guide

Observing and intervening in a running Woodpecker cluster

Before you start

This guide tracks the operational surface on current master for v0.1.46. Commands shown as steps are examples to adapt to your cluster; captured output and illustrative output are distinguished below.

Jump to command overview, incident workflows or script exit codes.

Every Woodpecker node serves an admin HTTP API on port 9091 (METRICS_PORT), and the wp CLI is bundled into the server images from v0.1.32 onward. Inside a pod it needs no configuration — the images set WOODPECKER_ENDPOINT=http://localhost:9091:

kubectl exec -it <woodpecker-pod> -- wp node list

Running outside Kubernetes

The seed endpoint discovers membership; it does not proxy requests to replicas. Pod FQDNs and IPs advertised in memberlist or segment metadata may be unreachable from your workstation. Expose each replica's admin HTTP port separately and map its original service address to that reachable origin:

# Run each port forward in a separate terminal.
kubectl -n woodpecker port-forward pod/wp-0 19091:9091
kubectl -n woodpecker port-forward pod/wp-1 29091:9091
kubectl -n woodpecker port-forward pod/wp-2 39091:9091
current-context: external
contexts:
  external:
    endpoint: http://127.0.0.1:19091
    node_admin_urls:
      "wp-0.wp-headless.woodpecker.svc.cluster.local:18080": http://127.0.0.1:19091
      "wp-1.wp-headless.woodpecker.svc.cluster.local:18080": http://127.0.0.1:29091
      "wp-2.wp-headless.woodpecker.svc.cluster.local:18080": http://127.0.0.1:39091

Use your actual advertised service addresses as keys. Repeated --node-admin-url KEY=URL flags merge into the context map and override the same key (last value wins). Lookup prefers the exact service address, then node ID, exact gossip address, service hostname and gossip hostname; without a match, the existing advertised host and admin-port behavior applies. Values are HTTP(S) origins, with optional ports and no credentials, path, query or fragment. Several replicas can map to localhost with different ports.

wp --context external node list --strict
wp --context external \
  --node-admin-url 'wp-0.wp-headless.woodpecker.svc.cluster.local:18080=http://127.0.0.1:49091' \
  node show wp-0

Mappings apply to memberlist fan-out, quorum reads and writes, and single-node targets. Original node and quorum identities stay intact; a mapped historical quorum address can be contacted even when absent from the current memberlist. An external URL is never a substitute for a quorum identity. Each destination must reach its intended replica; a Service that can send the request to any pod cannot stand in for per-replica access.

Reachable etcd endpoints are a separate requirement. Node mappings rewrite neither --endpoint nor --etcd, and do not create tunnels or change SDK gRPC destinations. For an isolated single-node command, an explicit target such as 127.0.0.1:19091 remains supported; most node commands still require a reachable Woodpecker seed for discovery. See the configuration reference.

Settings come from cli.yaml, looked for in $WOODPECKER_CLI_CONFIG, then the directory holding the wp binary, then $XDG_CONFIG_HOME/woodpecker/, then ~/.woodpecker/. The binary’s own directory comes second on purpose: a fixed cluster can be handed over as one folder, binary and config together, with nothing to pass per invocation. The working directory is deliberately not searched — adopting a config because of where the shell happens to be would let any directory point this tool at a cluster nobody chose.

Text output prints the resolved source and configured mappings on stderr; JSON/YAML output suppresses these diagnostics. Check the context and endpoint before acting:

wp: config /opt/wp/cli.yaml · context prod · endpoint http://10.0.1.5:9091
Every endpoint answers for one node. No admin endpoint queries its peers; each reports only its own state. wp is what fans out. This matters when you read any cluster-wide output: it is an assembled view, and a node that did not answer is missing from it rather than reported as empty. Commands report partial failures; where supported, --strict turns an incomplete view into an error. No node answering is an error, not evidence that a cluster is empty. Scan/probe/inspect have their own finding-based exit codes, explained below.

Field-by-field semantics for every endpoint live in common/http/README.md. This page covers when to reach for something and how to read the result.

Part 1 — Commands by level

Output examples below are captured from real runs unless marked otherwise. Command-only blocks are usage examples. Coverage is uneven, and the gaps are marked rather than glossed over: knowing in advance that something cannot be answered is worth more during an incident than discovering it there.

Groups nodes by region, availability zone and resource group. Use it to confirm placement spread — a quorum whose replicas share an AZ is a single-failure-domain quorum, whatever the replica count says.

wp node list gives the same membership as a flat table with each node’s advertised address and health. wp cluster health reduces it to red/yellow/green and exits 8 on a yellow finding, 9 on red.

Two narrower health questions have their own commands. wp node healthz returns the readiness probe Kubernetes itself acts on — the one that decides whether a pod receives traffic — and exits non-zero when it reports unhealthy. wp node log-health returns the node’s own per-log view of how reading and writing are going, derived from real operation outcomes rather than synthetic probes; when every tracked log is stalled or failed the endpoint answers 503 and the command reports the finding with the full per-log table rather than the status alone.

Can this node be terminated

$ wp node drain-status wp-wpawsusw-dab462fa-0

Drain status for wp-wpawsusw-dab462fa-0
  state:                 active
  remaining_processors:  68
  has_local_data:        true
  safe_to_terminate:     false

safe_to_terminate is decided by has_local_data alone — whether any segment data remains on local disk. remaining_processors is informational: processors are in-memory objects that vanish on shutdown, and the highest segment per log is deliberately never evicted, so the count does not reach zero.

Writer and logstore partial

What is being written on this node

$ wp logstore segments wp-wpawsusw-dab462fa-0

LOG_ID  SEG_ID  BACKEND        WRITABLE  FENCED  FINALIZED  ENTRIES  BLOCKS
31      0       stagedstorage  true      false   false      2        2
10      0       stagedstorage  true      false   false      2        2
8       0       stagedstorage  true      false   false      2        2

One row per segment with a live writer on this node. wp logstore segment-show adds the detail that matters when a write is not progressing: buffered bytes and entries, flush-queue depth against its capacity, sync-scheduler scheduled/running/waiting counts, and the last entry submitted for flushing.

Those fields separate the stalls that look alike from the outside:

  • buffer neither growing nor draining — nothing is arriving; the writer is not the problem
  • buffer growing, flush queue static — flushing is stuck
  • flush queue depth equal to capacity — backpressure is saturated
  • scheduler waiting high with nothing running — the scheduler is starved
  • last submitted flushing entry not advancing — submission is stuck

Is anything in flight right now

$ wp ops stats wp-wpawsusw-dab462fa-0

Capacity
  capacity:  1024
  in_use:    0  (0.0%)
  warn_age:  30000ms

Eviction Totals
  total:  0
  young:  0
  old:    0

The op registry tracks in-flight server-side operations, appends among them. in_use: 0 above means this node is serving nothing at that instant. To ask about one log, or about operations that have been running too long:

wp ops list <node> --type logstore.add_entry --log 42
wp ops list <node> --type logstore.add_entry --longer-than 30000

This is the most direct answer available to “is anything still writing to this log” and “has an append been outstanding too long”.

How far is this segment confirmed readable

$ wp logstore lac my-channel 3 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

Segment 3 of log my-channel — state Active, quorum 1 (es 3, wq 3, aq 2)

NODE            NODE_ID                 DURABLE_ENTRY  STATE
10.0.1.5:18080  wp-wpawsusw-dab462fa-0  4900           ok
10.0.1.6:18080  wp-wpawsusw-dab462fa-1  4821           ok
10.0.1.7:18080  wp-wpawsusw-dab462fa-2  4650           ok

quorum LAC: 4821 (aq=2 of 3 nodes at or past it)

Illustrative; the shape is the command’s, the numbers are not from a captured run.

Each node reports only how far it has durably written. No node can report the quorum’s position, because that is a property of the set: a position is confirmed readable once aq nodes have reached it, so the answer is the aq-th highest of the per-node figures — 4821 above, not the 4900 one node has reached alone.

The spread is the point. Nodes agreeing means the quorum is healthy and the tail is where it says; one node trailing, as the third does here, is a replica falling behind while the quorum still holds. If fewer than aq nodes answer, the command reports no value at all rather than the best it has — one node’s position presented as the quorum’s would overstate what is readable, which is the mistake the command exists to prevent.

A segment past Active takes its end from metadata instead, where it is authoritative: compaction, a processor close or idle eviction all leave a finished segment with no live writer on any node, and that is not a fault.

Local data and reclamation good coverage

From v0.1.45, GET /admin/instance/data reports which instances still hold data on a node:

$ wp instance data --all --strict

NODE          BUCKET    ROOT_PATH             LOGS  SEGMENTS  LIVE  SIZE_BYTES  PROCS  DELETE_STATE
woodpecker-0  a-bucket  in01-71ba8da6ff40c33  12    37        30    1234567     4
woodpecker-0  a-bucket  in01-dead0beef000000  4     9         9     3589343     0

The second row is the shape of an orphan: nothing running against it, and data that has not been touched in weeks. PROCS and the data’s age are what separate a genuine orphan from an instance created moments ago that has not flushed yet — on disk alone they are identical.

--strict is a safety flag rather than a formatting one. Without it an unreachable node is a row and the command still exits 0:

woodpecker-1  UNREACHABLE

WARNING: 1/2 nodes unreachable — their instances are not listed; do not delete on this view

With it, the same situation exits 6:

wp: StrictPartial: 1/2 nodes unreachable in strict mode

Metadata minimal

wp marking list / confirm handle compacted-mark distribution records; wp log readers reads reader checkpoints; wp logstore lac, wp segment probe, wp segment inspect and wp log scan resolve segment state and quorum from metadata. wp log skip-range list / add / remove manage operator declarations. These commands connect to etcd directly; quorum diagnostics also contact the replicas.

State the connection; do not expect it to be discovered. These commands read etcd, and the LogStore server does not, so the etcd section of its /admin/config is unvalidated — by default it points at loopback. Discovery is attempted as a convenience and refused when the address cannot work, naming the flag instead of spending the timeout. Expect to pass --etcd and --meta-prefix yourself. The prefix fails the more quietly of the two: a wrong one connects to the right etcd and lists an empty keyspace, so marking list prints the prefix it scanned for you to check against the client’s etcd.rootPath and woodpecker.meta.prefix.
Gap: there is still no way to list logs, and no command corrects a metadata record beyond marking confirm and the dedicated skip-range record. General metadata repair remains #254; do not substitute an unsupported wp meta command.

Readers partial

wp log readers lists a log’s readers with the position each opened at, the position each last read, and how long ago it reported. It reads metadata only, so it answers while a node is unreachable. wp logstore lac gives the tail those positions are measured against.

Gap: the reader side is per log — you have to name the log, and nothing lists which logs have readers at all, so a reader stuck on a log nobody is watching is still found by looking for it.

One constraint comes with the positions: they are republished every 30 seconds, so any comparison sampling faster than that sees every reader frozen and calls them all stuck.

Client-side writers and readers partial

The client library runs inside the embedding application. Its published read/write, compaction and truncation frontiers and append latencies belong to that process’s metrics endpoint, not to any Woodpecker node. Submitted position and oldest-queue age are not part of that exported surface.

They are still reachable from here. wp metrics takes an explicit host:port like any other target and scrapes whatever /metrics answers, and Milvus serves its own on 9091 as Woodpecker does, so the client side can be read without a dashboard:

wp metrics list <milvus-pod-ip>:9091 --filter woodpecker_client

metrics list shows metric names, types and series counts, not their values. Use metrics snapshot for per-label values; metrics watch sums all series of the named metric on that process, so it is not a per-log reader position.

wp --endpoint http://127.0.0.1:19091 metrics snapshot 127.0.0.1:49091 \
  --metric woodpecker_client_write_frontier_entry -o json

Here 19091 forwards a Woodpecker seed and 49091 forwards the embedding application (e.g. Milvus) metrics port. Inspect both segment and entry frontier with their labels; entry IDs restart in each segment. Useful ones are write_frontier_segment and write_frontier_entry — the position the quorum has confirmed, despite the name — together with the read frontier per reader, the compaction and truncation frontiers, and append latency.

Gap: how much the client has submitted but not yet had confirmed is not published, so the client side cannot say on its own whether a writer is backed up or simply idle. Read it from the node side instead: wp ops list <node> --type logstore.add_entry --longer-than 30000 names the appends the server has been holding too long, and their age is what an outstanding queue looks like from outside. The proposed submit-position/queue-age metrics were closed without merging (#371). A queue that never reached a node is not visible at all, but a full one only happens because the appends ahead of it are stuck server-side, and those do appear.

A node will not drain

Decommission waits for both processors and live local data to clear; terminate only when safe_to_terminate is true. When it does not, ask what the node is still holding:

# Inspect capacity and membership before removing a replica.
wp node list --strict
wp cluster health
wp node drain-status node-3

# Start decommission; acknowledge the interactive prompt, then watch in another terminal.
wp node decommission node-3
wp node drain-status node-3 -w

# If it does not finish, identify the data and live processors.
wp instance data node-3
wp logstore segments node-3
wp ops list node-3 --longer-than 30000

# Abort decommission if the operational plan changes.
wp node cancel-decommission node-3

Read the two together. drain-status says data remains; instance data attributes it to specific instances, which is what tells a cleanup still in flight apart from data stranded by an instance whose deletion never reached this node.

A row whose SEGMENTS exceeds LIVE is the common false alarm: those segments are already durable in object storage and scheduled for removal, and they never block termination. The has_local_data flag ignores them for exactly that reason.

A non-empty idle Active segment is now rolled by the client-side auditor using the same rolling policy as writes. With defaults, allow the 600s rolling interval plus an auditor tick (10s), and then compaction/cleanup time. The new empty Active segment has no data file and does not pin local data. This depends on a live client log handle and its auditor; a server alone does not coordinate rolling. If that client is gone, restore the application's writer lifecycle before expecting progress. A quiet log no longer needs an artificial append just to trigger rolling.

After safe_to_terminate, perform the pod/node replacement through your deployment tooling, then verify node list --strict, cluster gossip-diff and application write/read progress. A readmitted node must be observed in peers' views, not only its own view; rejoin after an abrupt death is improved but still subject to failure detection and network health. Recreate its port forward if running externally.

Reclaiming an orphaned instance

An instance’s local data is reclaimed when the control plane calls the delete on every node holding it. That broadcast is lossy — a node that was down at the time keeps its copy indefinitely, and nothing on it will ever notice.

# 1. Query. Stop here if any node failed to answer or reported scan errors.
wp instance data --all --strict

# 2. Decide: diff against your live-instance registry, then keep only rows with
#    PROCS == 0 and data old enough to rule out a just-created instance.

# 3. Delete — per node, only the nodes step 1 listed for that instance.
curl -X POST http://<node>:9091/admin/instance/delete \
  -H 'Content-Type: application/json' \
  -d '{"bucketName":"a-bucket","rootPath":"in01-dead0beef000000"}'

# 4. Poll until it is absent everywhere.
wp instance data --all --strict --bucket a-bucket --root in01-dead0beef000000

When using port forwards, curl must use the mapped reachable admin origin for that specific node; the CLI map does not rewrite raw curl requests. Deletion stays per-node and explicit on purpose: step 1 names exactly which nodes to send it to. Reclamation is asynchronous, so step 4 is a poll rather than a single check.

An incomplete view must not authorise a delete. A node that is merely unreachable holds intact data, and acting on a partial snapshot is the accident this workflow exists to prevent — hence --strict throughout.

Local disk filling up

Before expanding a PVC or scaling out, confirm the space is held by live instances. An instance whose data was never reclaimed keeps occupying the disk, and none of the usual remedies frees it:

wp instance data <node>

A row with PROCS at zero and a last-modified time long in the past, for an instance the control plane no longer knows about, is stranded rather than idle — reclaim it as above. If the usage is genuine, the sizing and watermark guidance is in disk-watermark.md.

Writes are not progressing

Check the embedding application is actually submitting writes, then inspect every replica involved. An empty op-registry snapshot on one node alone cannot prove the application is idle:

wp ops list <node> --type logstore.add_entry --log 42
wp ops list <node> --type logstore.add_entry --longer-than 30000

If nothing arrives on any involved replica, check whether the embedding application is stopped, idle, or blocked before its send path. Appends outstanding past 30 seconds point at the node side, and wp logstore segment-show narrows it to a stage using the buffer, flush-queue and scheduler counts listed in Part 1.

A single slow replica is not a reason to intervene. A write completes once the ack quorum is satisfied, so one lagging node is absorbed; a write only fails when enough replicas fail that the ack quorum cannot be reached.

Three commands answer this between them; there is no single view that assembles them, and none is needed, because each one rules out a different explanation.

QuestionCommandWhat the answer means
Is anything outstanding, and for how long? wp ops list <node> --type logstore.add_entry --longer-than 30000 Nothing listed: this node has no matching in-flight append at this instant; inspect the application and other replicas. An append held past 30s is the node’s own admission that it has not finished one.
Which stage is it held at? wp logstore segment-show Buffer, flush queue and scheduler counts separate a writer nothing is arriving at from one whose flushing has stopped. The readings and what each combination means are in Part 1.
Is the quorum still confirming, and which replica lags? wp logstore lac <logName> <segmentId> A confirmed position that advances between two runs means writing is working. One node trailing is a lagging replica the quorum absorbs; fewer than aq answering is a quorum that cannot confirm at all. 
# Example: my-channel has log ID 42, suspected segment 7.
wp logstore segments node-1 --log 42
wp logstore segment-show node-1 --log 42 --seg 7
wp logstore buffer node-1
wp logstore flush-queue node-1
wp ops list node-1 --type logstore.add_entry --log 42 --seg 7
wp logstore lac my-channel 7 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
# Repeat LAC and processor/ops samples; inspect the other quorum replicas too.

Run lac twice a little apart. The single most useful fact is whether the confirmed position moved, and one reading cannot tell you that.

Gap: how far the client has submitted is not published, so “submitted is ahead of confirmed” cannot be read directly. The outstanding appends in wp ops list are the substitute: they are the same backlog seen from the node that is holding it. Appends still queued inside the client, which never reached a node, are invisible — though a client queue only fills because what is ahead of it is stuck server-side, and that part does show.

Do not treat the CLI's --timeout as the application's append deadline. The client now defaults woodpecker.client.segmentAppend.sendTimeout to 2000ms for opening a stream and obtaining the first buffered response. Durability confirmation is a separate wait; retries, ordered queues, completion RPCs and rolling add time. Neither total append latency nor node readmission is promised to finish within 2s. Active quorum reads use segmentRead.activeTimeout (3000ms), settled reads use segmentRead.settledTimeout (20000ms), and state changes can trigger a settled-budget retry.

When a writer has to be made to start over, fencing is the mechanism: a fenced segment fails the next append, and the application is expected to reopen its writer, which re-establishes state through the normal path. A write completes at aq acknowledgements, so fencing one node removes one and the write carries on through the rest; interrupting it takes wq - aq + 1 nodes — two of three on the default quorum.

wp logstore fence-quorum <logName> <segmentId> --reason "stalled writer" \
    --etcd <endpoint> --meta-prefix <prefix>

It reads the quorum from the segment’s metadata, states how many nodes must be fenced before it touches anything, and without -y stops there. Naming fewer nodes than that with --nodes is refused outright rather than half-done: a fenced node fails the writer’s append, which rolls the segment, while the writer still reaches aq and carries on — state changed, nothing interrupted. If fewer nodes than required could be reached, the outcome is reported as a conflict rather than as success, for the same reason. wp logstore fence <node> remains for the cases that want exactly one node.

# Preview, with no write (exits 7 because acceptance was not given).
wp logstore fence-quorum my-channel 7 --reason "incident: stalled writer" \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

# After reviewing the segment and quorum, execute the same operation.
wp logstore fence-quorum my-channel 7 --reason "incident: stalled writer" \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker -y

# Verify the application reopens its writer, then inspect the newly active segment.
wp log scan my-channel --mode quick --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

Fencing is per segment and does not disable future writers or decommission nodes. A partial execution may already have fenced some nodes even when the command exits with a conflict; inspect the reported outcomes before retrying. The application must handle its append error and follow the normal reopen/rolling path.

Gap: a node fences through its live segment processor, so a node that has none refuses the request. It is reported with the node’s own reason and does not count towards the required number. For a stuck write the nodes holding the pending appends are the ones with live processors, so this rarely bites; a quorum whose processors have all been evicted cannot be fenced through this path at all.

Checking a whole log

Every command below starts from a segment id, which assumes you already suspect one. One sweep asks the question the other way round — does this log read through from end to end, and does what is on disk match what the metadata says:

wp log scan <logName> [--mode quick|raw] [--from-segment N] [--to-segment N] \
    --etcd <endpoint> --meta-prefix <prefix>
wp log scan my-channel --mode quick --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
# Narrow the expensive verification to the segment the first pass identified.
wp log scan my-channel --mode raw --from-segment 7 --to-segment 7 \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

One line per segment, then the findings. A clean log is a short report.

The following output is illustrative, not a captured cluster run.

SEGMENT  STATE      META LAST  REACHES  REPLICAS  VERDICT     DETAIL
0        Sealed     19         -        2/2       compacted   served from object storage; local replica copies are not the authority
1        Completed  19         0-19     2/2       ok
2        Completed  19         0-9      2/2       short       missing 10-19
3        Active     -1 (open)  0-7      2/2       open
VerdictWhat it means
okSome replica holds everything the metadata claims.
shortNo replica holds part of it, and at least one replica surveyed to the end of its own copy, so that is an answer rather than a gap in what was looked at.
openStill being written; the metadata records no last entry to measure against.
compactedOne shared object-storage copy, which this sweep does not read. The replicas’ local copies are not the authority in either direction.
reclaimedRetention is deleting it; a replica answering with nothing is expected.
unknownNothing was established — no replica answered, or every replica stopped its survey before the end of the segment.

The exit code says what the sweep established, which is not the same as what it found: 0 only when every segment was established and sound, 9 for a segment that is short or an open segment with a hole in the middle of what was written, and 8 when something could not be established. A sweep that learned nothing neither claims loss nor claims the log reads through, and it does not print a “no problem found” line next to a segment it could not judge. --strict promotes 8 to 9 for a script that wants an unestablished segment to fail its gate.

The two modes cost three orders of magnitude apart because they answer different questions:

ModeReadsAnswers
quick (default)the index and footer only — one trailer read per sealed segment, a few kilobytes whatever the segment weighsDoes the structure add up?
rawa verifying block survey using the data codec and checksumsWhich entry ranges can a reader obtain?

That is what makes sweeping a whole log affordable: a 256MB segment costs a quick scan the same as an empty one. An active segment has no index, so quick mode walks the chain for each block’s header, but not its body. Raw mode asks each node for the whole segment rather than taking its default bound of 64 blocks, which a default-sized segment exceeds at about 128 — and a survey that stopped before the segment’s end is read as a lower bound, never as missing data.

A replica that reports no local data at all is read through the compacted mark, the tombstone the cleanup writes before it drops a compacted segment’s data.log: with the mark the copy was reclaimed and the object is the authority, without it the replica looked and holds nothing, which is loss. The segment’s metadata state is a weaker second signal only — the cleanup keys off the object-storage footer and that mark, never off the state, and the metadata update after compaction is only warned about when it fails, so the state can lag the disk.

REACHES is the union across replicas, because a read needs one replica that holds the entry rather than a quorum. A replica short of that union is a replica that needs resyncing, not a loss, and is reported as such rather than as a fault. Entry ids restart at 0 in every segment, so a segment’s expected range is [0, lastEntryId] and nothing is derived from its neighbours; an Active segment’s -1 is open, never a mismatch.

Above the segment rows come the log-level findings. A gap in the segment ids is split by what to do about it: a node still holds the data (data nobody owns, which no reader reaches and no reclaim removes), no node holds it (the record is gone rather than the data), or no node could be asked. The walk for those gaps starts at the truncation point rather than above it, because truncation deliberately keeps the segment at the point — it is where readers resume — so that one record going missing is a loss and not retention. Only ids strictly below the point are expected to be gone.

The Active segments are reported without failing the sweep. A roll that finds a non-empty append queue leaves the previous segment Active until its completion RPCs finish while the new one takes writes, so more than one Active segment, and an Active segment that is not the newest, are both states a healthy log passes through. One observation cannot tell either from a segment left behind — what separates them is time — so the report says what it saw and says to re-run.

A scan summarizes coverage by segment; it does not provide the full block-level explanation. Use wp segment inspect for the question of whether the damage ends there.

A reader is not progressing

Two positions answer this, and both are readable. Where each reader has read to comes from metadata alone, so it survives the unreachable node that is often the reason for looking:

wp log readers <logName> --etcd <endpoint> --meta-prefix <prefix>

Each row carries the position the reader opened at, the position it last read, and how long ago it reported. Two of those rows mean something on their own:

ReadingWhat it means
no read since openThe reader has not reported a read since it opened. Its current position is the one it started at, not one it reached.
stale reportThe reader has stopped reporting. A reader tailing an idle log keeps republishing with an unchanged position, so a fresh report proves it is alive; silence is what a reader blocked inside a read looks like.

Then the tail to measure a position against:

wp logstore lac <logName> <segmentId> --etcd <endpoint> --meta-prefix <prefix>

The two are deliberately separate: the lag is not computed for you, because doing so would make an unreachable node fail a question that pure metadata already answers. Sample no faster than 30 seconds — positions are republished on that cadence, and a tighter interval shows every reader frozen and calls them all stuck.

Those two say where a reader is and where the confirmed tail is. When a reader is stuck between them, the next question is whether the data at that position can be read at all — and on which replicas:

wp segment probe <logName> <segmentId> [--from-entry N] [--max-entries N] \
    --etcd <endpoint> --meta-prefix <prefix>

Each replica attempts a bounded read of its own copy and reports what it holds and how far it got. Three readings mean different things, and the command states which one it found rather than leaving it to be derived:

ReadingWhat it means
every replica stops at the same entry, no errorThe data ends there. Nothing is wrong; the reader is waiting for something not yet written.
one replica stops earlier, with an errorThat replica is damaged and failover is covering for it. Nothing else reports this — reads keep working.
every replica fails at the same entryThe entry cannot be read anywhere. This is the case a reader waits on forever.

Probe stops where a read would, at the first block it cannot serve. That leaves the question a recovery turns on — is one block damaged, or is everything after it gone? — so the survey goes past that point:

wp segment inspect <logName> <segmentId> [--from-block N] [--max-blocks N] \
    --etcd <endpoint> --meta-prefix <prefix>

It walks each replica’s blocks and keeps going after one fails, which is what separates it from every read path. The findings under the table are the part to act on: which entries are damaged on which replica, whether another replica still holds them, whether every replica actually looked, and where readable data resumes — that last one is what decides whether a recovery gives up four entries or the rest of the segment.

ColumnWhat it means
READABLEall or none. A backend drops a block that fails its integrity check whole, so nothing in a failed block is readable.
RECOVERABLEThe prefix of a failed block whose own records still verify. No reader serves it; it is what a repair could salvage.
STATUSchecksum_failed, header_missing, data_unreadable, or data_incomplete — the last being an unsealed tail whose data has not been written yet, which is not damage.

Both commands are bounded by the node whatever you ask, because a full survey reads every byte of the segment on every replica. When the report says the bound rather than the segment ended the walk, raise --max-blocks or move --from-block. Note that --from-block is a per-replica position: replicas flush on their own timers, so the same block number covers different entries on different nodes, and a shorter replica returns nothing for a later page.

Read them in that order. lac and log readers are cheap and answer most stalls; log scan --mode quick is cheap too and is the one to reach for when no particular segment is suspected yet; probe costs a bounded read per replica; inspect reads every byte of the blocks it walks and is worth reaching for once probe has shown there is something to explain.

A transient checksum failure at the active tail is not enough to declare data lost. A block may still be written, and normal reads fail over when another replica holds the entry. Compare with the confirmed end and repeat a settled survey. A lost Active block header can stop the walk before any later entry is accounted for; a bounded or unreachable survey does not prove those entries are unreadable. Compacted segments use shared object storage: inspect/scan do not verify that authoritative object copy, and a probe served from it is one shared source rather than an independent copy per replica.

For a concrete investigation, suppose the reader of my-channel is parked in segment 7 around entry 50:

wp log readers my-channel --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
# Repeat after at least one 30s reporting interval and compare the CURRENT position.
wp logstore lac my-channel 7 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
wp segment probe my-channel 7 --from-entry 50 --max-entries 100 \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
wp segment inspect my-channel 7 --max-blocks 4096 \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

The reader checkpoint is the last published read position, not necessarily the exact entry now being retried; use probe/inspect to establish the boundary. If another replica serves it, preserve it and let failover work. If every replica has established the same unreadable span, proceed to the declaration workflow below.

Move a stalled reader past confirmed unreadable data

A skip range is an operator's acceptance of loss, not a repair. Both entry boundaries are inclusive. Declare only the span established by the survey; a reachable replica still able to read any part, an unreachable replica, a bound-limited survey or an unaccounted remainder refuses the normal declaration. --force bypasses that gate and still requires -y; it is not an alternative to collecting evidence.

# Example only: inspect established that entries 50 through 59 are unreadable everywhere.
wp log skip-range list my-channel --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

# Preview: inspect the quorum and print the loss, then stop without writing (exit 7).
wp log skip-range add my-channel 7 --from-entry 50 --to-entry 59 \
  --reason "incident: completed segment damaged on every replica; survey saved" \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

# Accept only after reviewing that evidence; this writes the declaration with CAS.
wp log skip-range add my-channel 7 --from-entry 50 --to-entry 59 \
  --reason "incident: completed segment damaged on every replica; survey saved" \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker -y

# Observe the declaration and the consumer's progress.
wp log skip-range list my-channel --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
wp log readers my-channel --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

Readers consult declarations only when their position is unchanged at a reporting tick. They jump to entry 60 in this example, or to the next segment if the span reaches the completed end. Healthy readers do not unconditionally skip readable entries, even if a forced declaration covers them. This is not immediate: reader reporting is 30s, cache refresh is asynchronous, and a cold cache can require a second tick. The client setting woodpecker.client.skipRangeRefreshInterval (default 10s) bounds refresh frequency, not the latency from the CLI write to a reader jump. Check the embedding application's WARN and woodpecker_client_reader_skip_range_skips_total, alongside actual consumer progress.

Once data has been restored, withdraw the declaration. This allows future reads to try the entries again; it neither restores bytes nor rewinds a reader that has already advanced. Reopen/replay through your application's reader lifecycle if recovery requires consuming those restored entries.

wp log skip-range remove my-channel 7 --from-entry 50 --to-entry 59 \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

# List across all logs, including declarations left behind by deleted logs.
wp log skip-range list --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
# For a deleted log whose original ID was 42, withdraw by ID (no log name).
wp log skip-range remove --log-id 42 7 --from-entry 50 --to-entry 59 \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

Overlapping declarations are coalesced; withdrawing a subset can split a range. Declarations persist until explicitly removed, including after truncation/deletion, and size/revision conflicts are reported rather than silently overwriting another operator's update.

Completed corruption, compaction and retention

The reader needs any replica that can serve the requested entry. Compaction needs one copy that passes integrity verification and covers the completed metadata LastEntryId. These are different checks: several replicas together may serve a range while no single intact copy can compact the whole segment.

Completed segmentReaderCompaction / action
One or two damaged replicas, an intact copy covers the endFailover can still read.Compaction tries replicas and can use the intact complete copy. No skip range needed.
No replica covers the original end or all relevant blocks are damagedWaits at the unreadable entry.The segment remains Completed. Establish loss, declare a skip range for readers, then expire data through retention when allowed.
Retention has marked the segment TruncatedA declaration handles an already parked reader; truncation alone is not that recovery step.The segment is no longer selected for Completed compaction; cleanup proceeds through normal retention.

An individual compaction failure is logged and skipped within the auditor's pass; it does not categorically block later Completed segments. Count/time budgets or cancellation can defer later work, and a bad early segment can consume that budget. Once Truncated, it is excluded from the next Completed candidate set. Frontiers alone are not proof that every earlier segment is sealed: inspect the per-segment state and the auditor's segmentsProcessed / segmentsCompacted / segmentsFailed / segmentsDeferred summary in the embedding application's logs.

Active recovery has a different boundary: on restart a damaged/incomplete record can truncate the local recovered prefix; reopening the writer fences and completes against the quorum-derived target. Do not treat that new completed end as the old end or automatically declare an Active tail lost. Recovery now emits segment recovery truncated at ... warnings with the file, log/segment, offset, entry and discarded bytes when the full scan stops on an incomplete/undecodable/unexpected record. This is diagnostic evidence, not a byte-level repair or a guarantee that every corruption is detected during recovery.

wp log scan my-channel --mode raw --from-segment 7 --to-segment 7 \
  --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
wp metrics report node-1 --scenario slow-compact --window 1m
wp marking list --log 42 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

Truncation is owned by the application's retention policy / SDK LogHandle.Truncate; there is no wp log truncate. Completed and Sealed segments can be truncated once the application's retention and reader-protection requirements permit. A skip range changes reading only: it does not repair bytes, seal the segment, shorten its metadata end or perform truncation.

Compacted-mark distribution parked for manual handling

wp marking list --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
wp marking list --all-states --log 42 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
wp node show node-3
# Only after verifying the unacked node is permanently removed / accounted for:
wp marking confirm 42 7 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker
# Verify the record is settled, not deleted.
wp marking list --all-states --log 42 --etcd etcd-a:2379 --meta-prefix by-dev/woodpecker

confirm moves PENDING_MANUAL to OPERATOR_CONFIRMED; it does not declare loss, retry compaction, repair a footer, or delete the record. The record is physically reaped by truncation. IN_PROGRESS/COMPLETED records are refused unless forced; an unreachable node can reconcile its mark when it returns.

Manual flush and compact are per-node tools

wp logstore force-flush node-1 --log 42 --seg 7
# Use only the exact completed LastEntryId obtained from coordinator metadata (99 here).
wp logstore compact node-1 --log 42 --seg 7 --expected-last-entry-id 99

Flush cannot repair checksum damage. Manual compact operates on one replica and is not a metadata repair transaction; the client auditor owns state advancement and mark distribution. Never guess its expected entry ID from one replica's longer tail. Check the backend and complete metadata before using this escape hatch.

Drift, diagnostics and supporting evidence

wp config diff --all --strict
wp env diff --strict
wp cluster gossip-diff --strict
wp config show node-1 -o json
wp env show node-1 -o json
wp node healthz node-1
wp node log-health node-1
wp metrics report --list
wp profile node-1 --type cpu --seconds 30 --output-file node1-cpu.pb.gz
wp logging get-level node-1
wp logging set-level node-1 --level debug
# Collect a short reproduction, then restore the previously recorded level.
wp logging set-level node-1 --level info

Config/env comparisons distinguish unreachable nodes from agreement; no replies fails the command. A partial comparison establishes agreement only among respondents. A readiness probe and per-log health answer different questions, so a healthy healthz does not establish reader progress. Treat a metrics report as supporting evidence and compare the actual labelled samples, operations and positions. For Kubernetes, wp k8s status, logs and scale print a plan by default; add -x only when execution is intended.

Correcting metadata

Use the dedicated diagnostics first. wp logstore lac shows a segment’s state and quorum membership, and wp marking list shows compacted-mark distribution records. Both connect to etcd directly, with the endpoint and prefix given explicitly.

Gap: there is still no way to list logs or perform general coordinator metadata repair (including a segment stuck in the wrong state). log readers does read checkpoints now, and log skip-range edits its specific declaration record; neither is a segment metadata editor. marking confirm settles a notification record rather than repairing one.

None of this will appear on the admin API. Metadata is owned by the client library, not by the LogStore nodes, which never connect to etcd — so it belongs to wp talking to etcd directly, with the connection stated rather than discovered.
