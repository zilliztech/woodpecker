Operations Guide

Observing and intervening in a running Woodpecker cluster

Before you start

Every Woodpecker node serves an admin HTTP API on port 9091 (METRICS_PORT), and the wp CLI is bundled into the server images from v0.1.32 onward. Inside a pod it needs no configuration — the images set WOODPECKER_ENDPOINT=http://localhost:9091:

kubectl exec -it <woodpecker-pod> -- wp node list

From outside the cluster there is one thing to know. Nodes advertise the address their own cluster knows them by — under Kubernetes the headless-service FQDN, which resolves only inside that network:

NAME                    ADDR                                                                                          STATE   AZ          RG
wp-wpawsusw-dab462fa-1  wp-wpawsusw-dab462fa-1.wp-wpawsusw-dab462fa-headless.woodpecker-pool.svc.cluster.local:18080  active  us-west-2c  default
wp-wpawsusw-dab462fa-5  wp-wpawsusw-dab462fa-5.wp-wpawsusw-dab462fa-headless.woodpecker-pool.svc.cluster.local:18080  active  us-west-2a  default

So running wp where those names resolve — in a Woodpecker pod, in a Milvus pod, or over a tunnel into the cluster network — is the path of least resistance. A single node can also be reached with kubectl port-forward.

Every endpoint answers for one node. No admin endpoint queries its peers; each reports only its own state. wp is what fans out. This matters when you read any cluster-wide output: it is an assembled view, and a node that did not answer is missing from it rather than reported as empty. Pass --strict to make an incomplete view an error instead of a silent gap.

Field-by-field semantics for every endpoint live in common/http/README.md. This page covers when to reach for something and how to read the result.

Part 1 — Commands by level

Every example below is captured from a real run. Coverage is uneven, and the gaps are marked rather than glossed over: knowing in advance that something cannot be answered is worth more during an incident than discovering it there.

Cluster and node good coverage

Who is in the cluster, and where

$ wp cluster info

Cluster Overview
  Cluster:     default
  Endpoint:    http://localhost:9091
  Total Nodes: 6

By State
  active: 6

default
└── us-west-2
    ├── us-west-2a
    │   └── default
    │       ├── wp-wpawsusw-dab462fa-5  active
    │       └── wp-wpawsusw-dab462fa-2  active
    ├── us-west-2b
    │   └── default
    │       └── wp-wpawsusw-dab462fa-4  active

Groups nodes by region, availability zone and resource group. Use it to confirm placement spread — a quorum whose replicas share an AZ is a single-failure-domain quorum, whatever the replica count says.

wp node list gives the same membership as a flat table with each node’s advertised address and health. wp cluster health reduces it to red/yellow/green and exits 8 on a yellow finding, 9 on red.

Can this node be terminated

$ wp node drain-status wp-wpawsusw-dab462fa-0

Drain status for wp-wpawsusw-dab462fa-0
  state:                 active
  remaining_processors:  68
  has_local_data:        true
  safe_to_terminate:     false

safe_to_terminate is decided by has_local_data alone — whether any segment data remains on local disk. remaining_processors is informational: processors are in-memory objects that vanish on shutdown, and the highest segment per log is deliberately never evicted, so the count does not reach zero.

Writer and logstore partial

What is being written on this node

$ wp logstore segments wp-wpawsusw-dab462fa-0

LOG_ID  SEG_ID  BACKEND        WRITABLE  FENCED  FINALIZED  ENTRIES  BLOCKS
31      0       stagedstorage  true      false   false      2        2
10      0       stagedstorage  true      false   false      2        2
8       0       stagedstorage  true      false   false      2        2

One row per segment with a live writer on this node. wp logstore segment-show adds the detail that matters when a write is not progressing: buffered bytes and entries, flush-queue depth against its capacity, sync-scheduler scheduled/running/waiting counts, and the last entry submitted for flushing.

Those fields separate the stalls that look alike from the outside:

  • buffer neither growing nor draining — nothing is arriving; the writer is not the problem
  • buffer growing, flush queue static — flushing is stuck
  • flush queue depth equal to capacity — backpressure is saturated
  • scheduler waiting high with nothing running — the scheduler is starved
  • last submitted flushing entry not advancing — submission is stuck

Is anything in flight right now

$ wp ops stats wp-wpawsusw-dab462fa-0

Capacity
  capacity:  1024
  in_use:    0  (0.0%)
  warn_age:  30000ms

Eviction Totals
  total:  0
  young:  0
  old:    0

The op registry tracks in-flight server-side operations, appends among them. in_use: 0 above means this node is serving nothing at that instant. To ask about one log, or about operations that have been running too long:

wp ops list <node> --type logstore.add_entry --log 42
wp ops list <node> --type logstore.add_entry --longer-than 30000

This is the most direct answer available to “is anything still writing to this log” and “has an append been outstanding too long”.

Gap: the last-add-confirmed position is not exposed on the admin surface. Without it you can see that a writer is busy, but not how far the confirmed tail has reached — which is what tells a lagging reader apart from one that has caught up. Tracked as part of the reader-diagnosis work.

Local data and reclamation good coverage

From v0.1.45, GET /admin/instance/data reports which instances still hold data on a node:

$ wp instance data --all --strict

NODE          BUCKET    ROOT_PATH             LOGS  SEGMENTS  LIVE  SIZE_BYTES  PROCS  DELETE_STATE
woodpecker-0  a-bucket  in01-71ba8da6ff40c33  12    37        30    1234567     4
woodpecker-0  a-bucket  in01-dead0beef000000  4     9         9     3589343     0

The second row is the shape of an orphan: nothing running against it, and data that has not been touched in weeks. PROCS and the data’s age are what separate a genuine orphan from an instance created moments ago that has not flushed yet — on disk alone they are identical.

--strict is a safety flag rather than a formatting one. Without it an unreachable node is a row and the command still exits 0:

woodpecker-1  UNREACHABLE

WARNING: 1/2 nodes unreachable — their instances are not listed; do not delete on this view

With it, the same situation exits 6:

wp: StrictPartial: 1/2 nodes unreachable in strict mode

Metadata minimal

wp marking list / confirm handle compacted-mark distribution records, and are the only commands that read cluster metadata.

Gap: metadata discovery is broken as shipped. wp marking takes its etcd endpoint from a node’s /admin/config, but the LogStore server never connects to etcd, so that field is an unset default and the command dials localhost:2379 and times out. Pass --etcd explicitly. Beyond this one command there is no way to list logs, inspect segment state, read quorum membership or see a reader’s position.

Readers none

Gap: there is no command to see which readers are attached to a log or where each has reached. The information exists — readers publish their position into metadata under a lease — but nothing surfaces it. A reader that has stopped advancing and one that has caught up are indistinguishable from the outside today.

Client-side writers and readers out of reach

Gap, and a permanent one: the client library runs inside the embedding application, so its pending-append counts, write frontier and append latencies are published to that process’s metrics endpoint. wp talks to Woodpecker nodes and cannot reach them. Client-side state has to be inferred from the node side — whether appends are arriving at all — or read from the application’s own metrics.

A node will not drain

Decommission waits for has_local_data to reach false. When it does not, ask what the node is still holding:

wp node drain-status <node>
wp instance data <node>

Read the two together. drain-status says data remains; instance data attributes it to specific instances, which is what tells a cleanup still in flight apart from data stranded by an instance whose deletion never reached this node.

A row whose SEGMENTS exceeds LIVE is the common false alarm: those segments are already durable in object storage and scheduled for removal, and they never block termination. The has_local_data flag ignores them for exactly that reason.

Reclaiming an orphaned instance

An instance’s local data is reclaimed when the control plane calls the delete on every node holding it. That broadcast is lossy — a node that was down at the time keeps its copy indefinitely, and nothing on it will ever notice.

# 1. Query. Stop here if any node failed to answer or reported scan errors.
wp instance data --all --strict

# 2. Decide: diff against your live-instance registry, then keep only rows with
#    PROCS == 0 and data old enough to rule out a just-created instance.

# 3. Delete — per node, only the nodes step 1 listed for that instance.
curl -X POST http://<node>:9091/admin/instance/delete \
  -H 'Content-Type: application/json' \
  -d '{"bucketName":"a-bucket","rootPath":"in01-dead0beef000000"}'

# 4. Poll until it is absent everywhere.
wp instance data --all --strict --bucket a-bucket --root in01-dead0beef000000

Deletion stays per-node and explicit on purpose: step 1 names exactly which nodes to send it to. Reclamation is asynchronous, so step 4 is a poll rather than a single check.

An incomplete view must not authorise a delete. A node that is merely unreachable holds intact data, and acting on a partial snapshot is the accident this workflow exists to prevent — hence --strict throughout.

Local disk filling up

Before expanding a PVC or scaling out, confirm the space is held by live instances. An instance whose data was never reclaimed keeps occupying the disk, and none of the usual remedies frees it:

wp instance data <node>

A row with PROCS at zero and a last-modified time long in the past, for an instance the control plane no longer knows about, is stranded rather than idle — reclaim it as above. If the usage is genuine, the sizing and watermark guidance is in disk-watermark.md.

Writes are not progressing

Start by establishing whether anything is arriving at all:

wp ops list <node> --type logstore.add_entry --log 42
wp ops list <node> --type logstore.add_entry --longer-than 30000

Nothing in flight and nothing long-running means the writers are quiet, not stuck — check whether the Milvus instance is stopped or disabled before looking further. Appends outstanding past 30 seconds point at the node side, and wp logstore segment-show narrows it to a stage using the buffer, flush-queue and scheduler counts listed in Part 1.

A single slow replica is not a reason to intervene. A write completes once the ack quorum is satisfied, so one lagging node is absorbed; a write only fails when enough replicas fail that the ack quorum cannot be reached.

Gap: the confirmed tail position is not exposed, so “stuck” cannot be told apart from “idle” from the server side alone. Compare against the write frontier in the client application’s own metrics in the meantime.

When a writer has to be made to start over, fencing is the mechanism: a fenced segment fails the next append, and the application is expected to reopen its writer, which re-establishes state through the normal path. Note that fencing a single node is not enough to trigger it — a write survives on the remaining replicas until enough of the quorum is fenced to break the ack quorum.

A reader is not progressing

Not yet supported. Readers do publish their position into metadata, but no command surfaces it, and the confirmed tail needed to judge lag is not exposed either — so a stalled reader and a caught-up one look the same. Corruption makes this worse: a checksum failure is currently reported as “data has not arrived yet”, which the reader retries indefinitely, so a genuine fault is indistinguishable from an idle log. Until that is fixed, the server-side WARN logged at the point of the checksum failure is the only signal.

Correcting metadata

Not yet supported. Beyond wp marking, metadata has no operational surface: no way to list logs, inspect segment state, read quorum membership, or repair a segment stuck in the wrong state. Metadata is owned by the client library, not by the LogStore nodes, so this will not appear on the admin API — it belongs to wp talking to etcd directly, with the connection configured explicitly rather than discovered.
