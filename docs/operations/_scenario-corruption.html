Data Corruption Diagnosis & Recovery

Establish the metadata boundary, identify readable copies and exact bad entries, then choose recovery without discarding healthy data.

Plan: preserve → compare → locate → choose → verify

StepCommandIntent
1log scan; deployment backupRecord the expected segment boundary and preserve deployment/data evidence before intervention.

1. Preserve evidence

Record the application checkpoint, log name/ID, segment ID, deployment version and replica locations. Preserve original replica files and relevant objects through your deployment's backup procedure before changing them. Capture the scan, probe and inspect results below; they are diagnostics, not a data backup.

The scan summary includes the metadata state and last entry. A Completed boundary of 99 expects entries 0..99. If a software bug is suspected to have written a wrong boundary, preserve the raw metadata through your existing etcd backup procedure and use the metadata escalation path.

2. Find the affected segment

wm log scan "$WP_LOG" --mode quick \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
wm log scan "$WP_LOG" --mode raw --from-segment "$WP_SEG" --to-segment "$WP_SEG" \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
# Example normal summary (DETAIL column omitted):
SEGMENT  STATE      META LAST  REACHES  REPLICAS  VERDICT
7        Completed  99         0-99     3/3       ok
8        Active     -1 (open)  -        3/3       open

# Example missing finalized tail, after a complete local survey:
SEGMENT  STATE      META LAST  REACHES  REPLICAS  VERDICT
7        Completed  99         0-49     3/3       short

# Example failed inspection requests:
SEGMENT  STATE      META LAST  REACHES  REPLICAS  VERDICT
7        Completed  99         -        0/3       unknown

The short example establishes a local coverage gap at 50..99; it does not explain the cause. Inspect/probe next. The unknown example establishes no coverage at all; inspect the per-replica DETAIL (for example HTTP 404, timeout or missing mapping) before deciding there is missing data.

VerdictWhat was established
okObserved local coverage matches the metadata expectation within this survey.
shortEvery relevant replica survey completed, and some expected range is absent from their combined local coverage. Any incomplete/unreachable alternative makes that missing range unknown.
unknownRequest, location, response or survey bound prevented a conclusion. Read the per-replica HTTP/error details.
open / local_emptyActive boundary remains unknown; replicas found no local durable entries. This is not automatically corruption.
compactedLocal copies are not authoritative. Scan has not verified shared object-storage data; use probe for actual reads.
reclaimedTruncated data is intentionally eligible for cleanup; absence is not automatically loss.

REACHES is the union of observed local ranges; '-' is no observed range. REPLICAS counts usable replies, not independent healthy copies. quick checks structure; raw verifies local block checksums. Neither establishes pending writes or end-to-end object readability.

3. Separate two damaged copies from all three

wm segment probe "$WP_LOG" "$WP_SEG" --from-entry 0 --max-entries 200 \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
wm segment inspect "$WP_LOG" "$WP_SEG" --max-blocks 4096 \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
# Two failed copies and one healthy copy, abbreviated:
NODE                    SERVED       OUTCOME       VERDICT
milvus-woodpecker-0      0-49 (50)    error         cannot serve
milvus-woodpecker-1      0-49 (50)    error         cannot serve
milvus-woodpecker-2      0-99 (100)   end_of_file   served

The healthy copy can support reader failover. Preserve it; do not declare readable entries lost. The CLI does not offer a generic copy/repair command. Recover damaged replicas through the supported deployment/recovery path, then verify their coverage. Compaction can still fail if it requires damaged copies.

# If all three instead stop before entry 50:
No replica can serve entry 50 ...
# Inspect may separately identify:
STATUS: checksum_failed
record stop: record_checksum_failed at entry 50
recoverable entries after the bad record: 51..99

Probe stops where sequential reading fails; inspect surveys beyond a bad block and can expose the tail. Confirm exact entry boundaries and each copy's result. A timeout, ambiguous path, 404 or cap_reached is not proof that an entry is unrecoverable. Object_storage replies inspect one shared copy, not three independent ones.

# Inspect excerpt for one node, assuming entry 50 occupies its own block:
BLOCK  ENTRIES  READABLE  RECOVERABLE  STATUS
0      0-49     all       -            ok
1      50-50    none      -            checksum_failed
2      51-99    all       -            ok

READABLE=none means normal reads reject that block. RECOVERABLE describes individually verified records inside a rejected block; it is evidence for repair, not a promise that the SDK can return them. Here the later block is independently valid. If entry 50 instead shares a damaged block with other entries, verify that whole block's consequences rather than assuming only 50 is affected.

4A. Accept a confirmed unreadable range

Use this branch only when every usable copy fails and the business accepts loss of the specific entries. The example assumes only entry 50 is confirmed unrecoverable, with 51..99 verified readable:

# Preview and check the evidence/gate; no -y means no commit (exit 7).
wm log skip-range add "$WP_LOG" "$WP_SEG" \
  --from-entry 50 --to-entry 50 --reason "All copies fail at 50; verified healthy tail"
# After explicit acceptance of losing entry 50:
wm log skip-range add "$WP_LOG" "$WP_SEG" \
  --from-entry 50 --to-entry 50 --reason "Accepted loss of entry 50" -y
wm log skip-range list "$WP_LOG"
# Successful add for log ID 42, segment 7:
Declared: log 42 segment 7 now skips 50-50
ResultMeaning
Gate refuses because a copy can servePreserve/read that copy; do not force past healthy data just to make a command pass.
Acceptance not givenExpected preview behavior, no declaration committed.
Declaration committedReaders can skip the inclusive range. Files remain damaged; compaction is not repaired by the declaration.

Keep the same stalled reader running. Wait for refresh/report timing and verify it crosses 50 and reaches 99. For a reader returning original entries 0..99, skipping just 50 means 99 returned records; record IDs and application checkpoints establish what was lost. Removing the declaration does not restore data.

4B. Escalate a proven metadata bug

If independent file validation and acknowledged-write history disagree with the coordinator's last entry or state, preserve the evidence and identify the responsible software fix. Do not lower the boundary merely because a replica lost acknowledged data. This handbook's CLI does not include a general metadata patch operation; arrange a reviewed, version-specific repair with the maintainers.

Metadata inspection and controlled patch tooling is tracked in PR #423. Follow its final merged command guide when available; the commands are not part of this source snapshot.

5. Close the compaction/retention loop

Reader recovery and compaction are separate. Skip-range does not fix a damaged Completed copy. Later eligible segments can be compacted independently; the damaged segment may continue failing until repaired or deliberately retired.

After the application has durably checkpointed beyond the damaged segment, use its supported Woodpecker SDK truncation/checkpoint workflow to retire that range. For example, advancing the frontier into segment 8 permits retiring segment 7; truncating to 7:99 retains segment 7 itself. This CLI snapshot has no log truncate command.

A live application log handle/auditor marks earlier finalized segments Truncated in subsequent rounds, then applies retention and reader protection. No active auditor means the background transition will not occur. Physical deletion is asynchronous; a metadata backup cannot restore deleted files. Use scan and marking to observe the result:

wm log scan "$WP_LOG" --mode quick \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
wm marking list
Compacted-mark notification is pending manual handling

Inspect marking records and verify the unacked node's disposition before using wm marking confirm "$WP_LOG_ID" "$WP_SEG". It settles notification retries, not data corruption or segment metadata, and the record remains until truncation reaps it.

6. Verify the chosen recovery

sleep 35
wm log readers "$WP_LOG"
wm segment probe "$WP_LOG" "$WP_SEG" --from-entry 51 --max-entries 100 \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"

For read recovery, require the same reader and application checkpoint to progress through the verified tail. For replica repair, re-probe/inspect every repaired copy. For retirement, expect Truncated/reclaimed rather than readable data and verify the auditor no longer attempts compaction on the retired segment. In a controlled lab, restore original files before removing skip declarations and verifying the original full record count.
