Log progress & retention

wp log readers

Show where each of a log's readers has read to

wp log readers <logName> [flags]

Parameters to know

No additional operation-specific flags. Connection settings come from CLI setup.

Etcd connection flags: see CLI setup.

Demo

wp log readers my-channel --etcd 127.0.0.1:32379 --meta-prefix milvus-prod/woodpecker

Output and interpretation

READER      OPEN_POS  CURRENT  LAST_REPORT  OPEN_FOR  STATE
reader-123  7:0       7:50     3s           5m        live

Reads leased registration under readers/<logId>/. No live readers means no usable registration here, not no Milvus queries. Reports normally refresh every 30 seconds; compare two snapshots to establish progress. Lease expiry or wrong namespace can hide readers.

Finding or error example 
Log my-channel (id 42) — no live readers
# Or a stale report: check activity and namespace before declaring a stall.
Complete command help 
Show where each of a log's readers has read to

Usage:
  wp log readers <logName> [flags]

Flags:
      --etcd string                   Etcd endpoints (comma-separated); overrides context etcd.endpoints and metadata admin discovery
      --etcd-cacert string            Local etcd TLS CA cert file; overrides context and discovery
      --etcd-cert string              Local etcd TLS client cert file; overrides context and discovery
      --etcd-key string               Local etcd TLS client key file; overrides context and discovery
      --etcd-password string          Etcd auth password; overrides context and discovery
      --etcd-tls-min-version string   Etcd TLS min version (1.0/1.1/1.2/1.3); overrides context and discovery
      --etcd-username string          Etcd auth username; overrides context and discovery
  -h, --help                          help for readers
      --meta-prefix string            Full metadata prefix; overrides context etcd.meta_prefix and admin discovery

wp log scan

Compare metadata with replica local coverage; raw verifies local block checksums

wp log scan <logName> [flags]

Parameters to know

Parameter / type Use and default
--bucket string Storage bucket; pair with --root-path to locate unloaded or empty segments
--from-segment int First segment to scan
--mode string quick reads only structure and metadata; raw reads the data through the real checksums (default "quick")
--root-path string Storage instance root path; pair with --bucket
--to-segment int Last segment to scan (default: the newest) (default -1)

Etcd connection flags: see CLI setup.

Demo

wp log scan my-channel --mode raw --bucket milvus-bucket --root-path milvus/wp --etcd 127.0.0.1:32379 --meta-prefix milvus-prod/woodpecker

Output and interpretation

SEGMENT STATE META LAST REACHES REPLICAS VERDICT
1 Active -1 (open) - 3/3 open
Per replica: local_empty / none / no_local_blocks

REACHES is the union of observed local ranges; - means none observed. 3/3 counts usable inspection responses, not three healthy data copies. quick checks structure; raw verifies local blocks. Sealed/compacted data in object storage is not verified. Explicit bucket/root-path resolves empty or unloaded targets; pending writes are not inspected.

Finding or error example 
unknown: HTTP 404 ... / short: missing entries 50..99

wp log skip-range add

Declare an entry range unreadable so readers move past it.

wp log skip-range add <logName> <segmentId> [flags]

Parameters to know

Parameter / type Use and default
--force Declare the range even though a replica can still read part of it
--from-entry int First entry to skip (inclusive) (default -1)
--reason string Why these entries are being given up (required)
--to-entry int Last entry to skip (inclusive) (default -1)
-y, --yes Proceed without the confirmation prompt

Etcd connection flags: see CLI setup.

Demo

wp log skip-range add my-channel 0 --from-entry 50 --to-entry 50 --reason "Confirmed unrecoverable entry" --etcd 127.0.0.1:32379 --meta-prefix milvus-prod/woodpecker

Output and interpretation

Ranges and reasons / preview or committed declaration

A declaration makes readers skip accepted data loss; it does not fix replicas or advance compaction. Entry bounds are inclusive. add previews before confirmation (-y accepts); remove does not restore skipped/reclaimed data. Inspect all replicas and the healthy tail first.

Finding or error example 
Gate refuses because a replica can serve / acceptance not given
Complete command help 
Declare an entry range unreadable so readers move past it.

This gives up data. Entries in the range are never delivered to any reader of this log
again, and nothing restores them: withdrawing the range only exposes whatever is still on
disk. So the quorum is asked first, and a replica that can still read part of the range
refuses the declaration.

Usage:
  wp log skip-range add <logName> <segmentId> [flags]

Flags:
      --etcd string                   Etcd endpoints (comma-separated); overrides context etcd.endpoints and metadata admin discovery
      --etcd-cacert string            Local etcd TLS CA cert file; overrides context and discovery
      --etcd-cert string              Local etcd TLS client cert file; overrides context and discovery
      --etcd-key string               Local etcd TLS client key file; overrides context and discovery
      --etcd-password string          Etcd auth password; overrides context and discovery
      --etcd-tls-min-version string   Etcd TLS min version (1.0/1.1/1.2/1.3); overrides context and discovery
      --etcd-username string          Etcd auth username; overrides context and discovery
      --force                         Declare the range even though a replica can still read part of it
      --from-entry int                First entry to skip (inclusive) (default -1)
  -h, --help                          help for add
      --meta-prefix string            Full metadata prefix; overrides context etcd.meta_prefix and admin discovery
      --reason string                 Why these entries are being given up (required)
      --to-entry int                  Last entry to skip (inclusive) (default -1)
  -y, --yes                           Proceed without the confirmation prompt

Etcd connection flags: see CLI setup.

Output and interpretation

Removed: ...
# Inspect list afterward to verify the remaining intervals.

A declaration makes readers skip accepted data loss; it does not fix replicas or advance compaction. Entry bounds are inclusive. add previews before confirmation (-y accepts); remove does not restore skipped/reclaimed data. Inspect all replicas and the healthy tail first.

Finding or error example 
Error: StateConflict: ...
# Refresh and retry after reviewing concurrent changes.
Complete command help 
Withdraw a declared range, so readers stop skipping it.

Withdrawing does not restore anything: it only lets readers try the entries again, which
is what to do once a replica has been rebuilt. A reader that already moved past the range
does not come back for it.

wp log truncate

Advance the truncation frontier with the SDK's metadata-update semantics and additional operator guards. Defaults to preview. The target must be a non-empty Completed or Sealed segment. Subsequent auditor rounds mark earlier finalized segments Truncated and reclaim data according to retention and reader protection. The frontier segment is retained. Apply can cause permanent data loss; verify application checkpoints first.

wp log truncate <logName> [flags]

Parameters to know

Parameter / type Use and default
--apply Advance the frontier (default: preview only)
--backup string New pre-change backup file; never overwritten
--entry int Target entry ID (required) (default -1)
--expected-revision int Log record ModRevision from preview
--reason string Operator reason recorded in audit
--segment int Target segment ID (required) (default -1)

Etcd connection flags: see CLI setup.

Demo

Verify the application checkpoint first. For the preview/apply sequence and asynchronous cleanup, follow the retention workflow.

wp log truncate my-channel --segment 8 --entry 0 --etcd 127.0.0.1:32379 --meta-prefix milvus-prod/woodpecker

Output and interpretation

{
  "applied": false,
  "unchanged": false,
  "before": {
    "revision": 17099,
    "metadata": {
      "truncated_segment_id": "6",
      "truncated_entry_id": "99"
    }
  },
  "after": {
    "revision": 17099,
    "metadata": {
      "truncated_segment_id": "8",
      "truncated_entry_id": "0"
    }
  },
  "target_segment_revision": 175,
  "snapshot_revision": 18000
}

Preview requires a non-empty Completed/Sealed target and entry within 0..lastEntryId. Apply requires --apply --expected-revision (the log before.revision), --reason and a new --backup; no offline flag is required. The log and target revisions are compared and an audit record is written atomically. The frontier segment stays retained; earlier finalized segments become eligible for auditor/retention/reader-protected cleanup. Unchanged frontier means applied=false, unchanged=true with no artifacts. Verify application checkpoints first: metadata backup cannot restore reclaimed data.

Finding or error example 
Error: StateConflict: truncation cannot move backward or restore deleted data
# Active/empty targets, identity mismatches, stale revisions and concurrent updates are also rejected.
