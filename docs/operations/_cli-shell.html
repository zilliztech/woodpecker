Interactive shell

Source-build feature: wp shell is not included in v0.1.47. Build a checkout containing the command with make wpcli and run ./bin/wp shell --help to check availability. Examples below use wp from that build. Output is illustrative; replace names, prefixes and storage locations with those of your deployment.

Keep one terminal open while operating a multi-tenant Woodpecker service. Select the service once, then explicitly connect the tenant whose metadata you want to inspect. Inside the session, omit the leading wp; existing operation arguments, previews and confirmations still apply.

1. Configure and select the service context

A service context is required. For a Helm installation accessed from outside Kubernetes, first establish the Admin port forwards described in CLI setup. Save this example as ~/.woodpecker/cli.yaml:

current-context: milvus-prod
contexts:
  milvus-prod:
    endpoint: http://127.0.0.1:19091
    timeout: 10s
    node_admin_urls:
      milvus-woodpecker-0: http://127.0.0.1:19091
      milvus-woodpecker-1: http://127.0.0.1:29091
      milvus-woodpecker-2: http://127.0.0.1:39091
  milvus-staging:
    endpoint: https://wp-staging.example.com:9091

endpoint is the Admin seed. node_admin_urls maps the node IDs or advertised addresses returned by your cluster to workstation-accessible Admin origins. A reachable seed alone does not make the other replicas reachable. The staging origin above is a placeholder; configure its actual mappings when required.

wp shell --context milvus-prod

For a configuration file in another location, set the environment variable in the same terminal before starting:

export WOODPECKER_CLI_CONFIG=/path/to/cli.yaml
wp shell --context milvus-prod

Without --context, an interactive wp shell always displays a context selector, even when a current context exists. Enter a displayed number or exact name; Enter accepts a valid current-context. Piped input requires an explicit --context. Missing or invalid configuration reports the relevant configuration path and setup instructions. See CLI setup for the full configuration search order.

Service context: milvus-prod
Config file:     /Users/example/.woodpecker/cli.yaml
Admin endpoint:  http://127.0.0.1:19091
Node mappings:   3
Tenant metadata: not configured

wp[context=milvus-prod | meta=disconnected]>

The prompt identifies two independent targets: context is the Woodpecker service cluster; meta is the selected tenant connection, or disconnected. The latter means no tenant is configured, not a network health verdict. Entering the shell does not contact the services or automatically attach the context's etcd settings. The shell pins its chosen service endpoint rather than inheriting WOODPECKER_ENDPOINT.

2. Connect the tenant: etcd, metadata prefix and storage

From the interactive prompt, connect using the tenant's workstation-accessible etcd endpoint and complete Woodpecker metadata prefix. Keep this example on one line when entering it:

connect tenant-a --etcd 127.0.0.1:32379 --meta-prefix tenant-a/woodpecker --bucket tenant-a-bucket --root-path milvus/wp
Parameter Meaning and requirement
tenant-a Required operator-selected connection name, displayed as meta=tenant-a. It is an alias; it does not derive or change the actual metadata prefix.
--etcd Required reachable etcd endpoint; comma-separate multiple endpoints. Outside Kubernetes, use the forwarded or otherwise reachable address.
--meta-prefix Required complete metadata namespace configured by the client, for example tenant-a/woodpecker. Do not supply a particular log key or confuse it with the physical storage root.
--bucket Physical storage bucket for this tenant. Optional for metadata-only operations; provide together with --root-path.
--root-path Physical storage instance root, for example milvus/wp. Provide together with --bucket; it need not equal the metadata prefix.
--etcd-username / --etcd-password Credentials when etcd authentication is enabled. Each new connection starts with fresh settings; omitted credentials are not inherited from the previous tenant.
TLS endpoint Use an https:// etcd endpoint or supply certificate flags to enable TLS. There is no separate --etcd-tls switch in this interface.
--etcd-cacert Local CA certificate file when needed. Certificate flags enable TLS.
--etcd-cert / --etcd-key Local client certificate and private key for mutual TLS; provide both.
--etcd-tls-min-version Minimum TLS version when TLS is enabled: 1.0, 1.1, 1.2 or 1.3; default 1.2. 
Service context: milvus-prod
Tenant:          tenant-a
Etcd endpoints:  127.0.0.1:32379
Meta prefix:     tenant-a/woodpecker
Bucket:          tenant-a-bucket
Root path:       milvus/wp

wp[context=milvus-prod | meta=tenant-a]>

Success verifies an etcd read under the supplied prefix, even if it is empty. It does not establish that you selected the intended tenant, that its quorum belongs to this service context, or that its data is healthy. Check status and the returned metadata before operating. connect --help lists the complete connection flags.

Metadata-only and TLS connection examples 
# Metadata-only connection; no bucket/root-path is needed.
connect tenant-a --etcd 127.0.0.1:32379 --meta-prefix tenant-a/woodpecker

# Custom CA and client certificates; use files on this workstation.
connect tenant-a --etcd etcd.example.com:2379 --meta-prefix tenant-a/woodpecker --etcd-cacert /path/to/ca.pem --etcd-cert /path/to/client.pem --etcd-key /path/to/client-key.pem

Each successful connect replaces the whole tenant connection. A metadata-only reconnect also clears a previous bucket/root-path. A failed connection retains the previous selected tenant and reports that the selection is unchanged.

Connecting makes the required parameters available; it does not make every operation succeed. Physical reads also require reachable quorum node Admin endpoints, and mutation commands still require their operation-specific evidence and safeguards. Raw etcd commands use the literal key/prefix you supply; --meta-prefix does not automatically scope or prepend raw etcd paths.

meta log list
log readers application-log
log scan application-log --mode raw
segment inspect application-log 0

# Override data location for this one operation only.
segment probe application-log 0 --bucket another-bucket --root-path another/root

Use actual log names from meta log list and segment IDs from meta segment list application-log. A per-command override does not modify the next command's defaults. When a tenant storage location is attached, instance data and node log-health also inherit it as a filter (their root flag is --root). They remain usable without a tenant connection. This shell's explicit storage-location rule does not change the existing non-interactive CLI's discovery behavior.

4. Inspect the session with status

status

Service context: milvus-prod
Config file:     /Users/example/.woodpecker/cli.yaml
Admin endpoint:  http://127.0.0.1:19091
Node mappings:   3
Tenant:          tenant-a
Etcd endpoints:  127.0.0.1:32379
Meta prefix:     tenant-a/woodpecker
Bucket:          tenant-a-bucket
Root path:       milvus/wp

status reads local session settings without making network requests, so it works while services are down or no tenant is attached. When credentials are configured, it reports that authentication is configured without printing them. An empty bucket/root-path means physical inspection needs explicit values.

status --check

Admin check: OK
Etcd check: OK

The check form also prints the session configuration, then performs bounded Admin and etcd checks. Read the two results separately. When disconnected it prints Etcd check: skipped (no tenant configured); a failed Admin check does not hide the separate etcd result. Neither check verifies application progress or physical data integrity.

5. Disconnect or switch a service/tenant

disconnect
status
use milvus-staging
connect tenant-b --etcd 127.0.0.1:42379 --meta-prefix tenant-b/woodpecker
status

disconnect clears the entire tenant connection, including credentials, TLS, metadata prefix and storage location. It retains the service context. A successful use <context> switches the service and clears any tenant attachment; connect the intended tenant again. A failed context selection leaves the current service and tenant unchanged.

wp[context=milvus-prod | meta=tenant-a]> disconnect
Tenant metadata: not configured
wp[context=milvus-prod | meta=disconnected]> use milvus-staging
Service context: milvus-staging
Config file:     /Users/example/.woodpecker/cli.yaml
Admin endpoint:  https://wp-staging.example.com:9091
Node mappings:   0
Tenant metadata: not configured
wp[context=milvus-staging | meta=disconnected]>

Session-local switching does not write current-context or affect another terminal. Inside the session, ctx list and ctx view inspect saved CLI configuration; use status to inspect the active tenant attachment. Use use for session-local switching. The existing ctx use command is a persistent change to the original configuration file and does not retarget this running session; invoke it only when you intend to change the default on disk. Exit and start a new shell to reload an edited configuration file.

6. Interpret missing configuration and connection failures

If a metadata-dependent command runs while disconnected, it fails before contacting Admin or etcd, even if the service context contains etcd settings or you pass connection flags on that operation:

wp[context=milvus-prod | meta=disconnected]> meta log list
wp shell: Prerequisite: no tenant metadata connection configured.
Connect with: connect <tenant> --etcd <host:port> --meta-prefix <prefix>.
Physical inspection also needs --bucket <bucket> --root-path <root-path>.
Run status to view the session
Result Meaning / next step
no tenant metadata connection configured Run connect, then retry. Service-only commands and help remain available.
physical inspection requires --bucket ... and --root-path ... Supply the paired location flags on scan/inspect/probe, or reconnect the tenant with both. No physical inspection has started.
tenant connection failed ...; active tenant unchanged: ... Check endpoint forwarding, authentication and local TLS files. The previous tenant remains selected, or the session stays disconnected. Run status before continuing.
Admin check: failed ... / Etcd check: failed ... Configuration exists but that check could not succeed. A timeout or authentication failure is different from a missing connection configuration; the selected context/tenant remains intact.

7. Help, completion and exit

help
connect --help
help segment inspect
ctx list
exit

Tab completes command/flag names and context names after use. Arrow keys recall in-memory history; connect and credential-bearing commands are excluded from history. Ctrl+C cancels the current operation and returns to the prompt. Use exit, quit or Ctrl+D to leave.

This is a command session, not bash/zsh: quoted arguments work, but environment-variable expansion, pipes and redirection are not evaluated. Run exports and port forwards in your ordinary terminal. Enter each example operation as a separate command. Existing command findings can return errors while the shell remains open for further diagnosis.

wp shell

Open an interactive operational shell. Without --context, choose a context from cli.yaml.

wp shell [flags]

Parameters to know

No additional operation-specific flags. Connection settings come from CLI setup.

Demo

wp shell --context milvus-prod
# Inside the interactive session:
status
connect tenant-a --etcd 127.0.0.1:32379 --meta-prefix tenant-a/woodpecker --bucket tenant-a-bucket --root-path milvus/wp
meta log list

Output and interpretation

wp[context=milvus-prod | meta=disconnected]>
# After connect succeeds:
wp[context=milvus-prod | meta=tenant-a]>

The service context is required; attaching a tenant is explicit and optional. Service commands work while disconnected. Metadata operations require connect, and interactive scan/inspect/probe also require bucket/root-path. status shows local selection; status --check checks reachability. Switching service contexts clears the tenant connection. This source-build feature is not included in v0.1.47.
