Read Stalls

Decide whether the reader is caught up, not reporting, unable to reach a replica, or blocked by unreadable data.

Plan: position → tail → actual reads → recovery

StepCommandIntent
1log readers, twiceIdentify the reader and determine whether its reported position moves.
2logstore lac; log scanCompare the reader with confirmed progress and the authoritative segment state/boundary.
3segment probeAsk all quorum members to actually read at the suspected position.
4segment inspect; ops list/showLocate damaged blocks/records or a long-running request; distinguish data failures from transport failures.
5Repeat the reader sample and application readVerify the same reader resumes and reaches the expected tail after the appropriate recovery.
{{WORKFLOW_CONNECTION}}

1. Observe the reader twice

wm log readers "$WP_LOG"
sleep 35
wm log readers "$WP_LOG"

Readers normally report on a 30-second cadence. A single unchanged checkpoint is not a stall. For example, the application last returned 7:49 and is waiting for 7:50; the registry can report that pending position:

READER       OPEN_POS  CURRENT  LAST_REPORT  OPEN_FOR  STATE
reader-123   7:0       7:50     3s           5m        live
# A later sample still reports CURRENT 7:50.
ResultInterpretation / next step
Position advancesReading is progressing. Compare application consumption/processing latency instead of treating this as a Woodpecker read stall.
Fresh report, unchanged positionThe reader is reporting, but could simply be caught up. Compare with the confirmed tail next.
stale reportReporting is not keeping up. Inspect client logs, blocked calls and connectivity; this alone does not prove corruption.
no read since openNo new position has been reported since opening; this is not proof of an unreadable first entry.
no live readersNo usable leased reader registration exists under this metadata namespace. Check context/prefix, client activity and leases. Milvus query traffic does not imply an open WAL reader.

CURRENT is the reader's reported position at a report tick, not a count of delivered records or an exact last-returned entry. Use application logs/checkpoints to identify the next entry actually required.

2. Compare the confirmed tail and metadata

wm logstore lac "$WP_LOG" "$WP_SEG"
wm log scan "$WP_LOG" --from-segment "$WP_SEG" --to-segment "$WP_SEG" \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
# Illustrative scan summary:
SEGMENT  STATE      META LAST  REACHES  REPLICAS  VERDICT
7        Completed  99         0-99     3/3       ok

NODE_ID                 DURABLE_ENTRY  STATE
milvus-woodpecker-0      99             ok
milvus-woodpecker-1      99             ok
milvus-woodpecker-2      99             ok
quorum LAC: 99 (aq=2 of 3 nodes at or past it)

If the application needs 50 and the finalized boundary is 99, there should be data to read. If an Active reader is already at the current tail, waiting can be normal. Active metadata is not a final boundary. LAC establishes confirmed progress, not checksum integrity; for Completed/Sealed segments the CLI can use metadata when no live writer remains.

3. Read the suspected position on every replica

wm segment probe "$WP_LOG" "$WP_SEG" \
  --from-entry 50 --max-entries 100 \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"

A readable Completed segment returns the requested range through its final entry. These excerpts keep only the result columns:

# Normal: all three nodes reach the expected final entry 99.
NODE_ID                 SOURCE      SERVED      OUTCOME      VERDICT
milvus-woodpecker-0      local_disk  50-99 (50)  end_of_file  served
milvus-woodpecker-1      local_disk  50-99 (50)  end_of_file  served
milvus-woodpecker-2      local_disk  50-99 (50)  end_of_file  served

# Abnormal: entry 50 cannot be read on any copy.
NODE_ID                 SOURCE      SERVED   OUTCOME  VERDICT
milvus-woodpecker-0      local_disk  nothing  error    cannot serve
milvus-woodpecker-1      local_disk  nothing  error    cannot serve
milvus-woodpecker-2      local_disk  nothing  error    cannot serve

SERVED=50-99 (50) means 50 returned entries, IDs 50 through 99 inclusive. nothing means no entry was returned from this requested start, not that the entire segment is empty. Read DETAIL for the actual error before deciding on recovery.

Probe resultMeaning / action
served, end_of_file at 99The requested finalized tail was readable. Investigate client handling, retries or processing above Woodpecker.
cap_reachedThe requested window ended; this is not EOF. Increase max-entries or move from-entry.
Active: entry_not_found / no local dataThe final boundary is unknown. It may be an unwritten/caught-up tail; pending writes are not established by a no-local-data response.
One or two replicas fail; another reaches 99Failover can cover the failed copies. Preserve the healthy copy and diagnose the unhealthy nodes.
All reachable replicas fail at required entry 50There is no usable local alternative at that position. Inspect the exact damage and healthy tail before any data-loss decision.
unreachable / not in memberlist / HTTP 404 / cannot answerCoverage is not established. Fix connectivity, mapping or storage-instance selection; do not interpret a failed request as confirmed data loss.

For Sealed segments, SOURCE=object_storage means the probe reads the shared compacted object. Three such replies are three reads of one shared copy, not three independent copies. See probe parameters and output fields.

4. Locate the blocker

wm segment inspect "$WP_LOG" "$WP_SEG" --max-blocks 4096 \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
w ops list "$WP_NODE" --type logstore.get_batch_entries \
  --log "$WP_LOG_ID" --seg "$WP_SEG" --longer-than 30000
# Copy a real OP_ID from the list:
w ops show "$WP_NODE" --op-id REAL_OP_ID

Inspect walks beyond the first damaged block and can expose recoverable records after the bad entry. checksum_failed/record_checksum_failed differs from a bound or missing local data. Ops list is only the instantaneous in-flight registry; empty output on one node does not prove the client is idle. Check the other quorum nodes too.

5. Choose recovery and prove progress

EvidenceRecoveryVerify
Endpoint/mapping failureRestore the relevant connection or node availability.Probe now returns usable results; application reader progresses.
Healthy tail; no physical faultInspect/fix the client retry, reporting or application processing path.Same reader resumes; application checkpoint advances.
Confirmed unrecoverable range on every copyFollow the corruption workflow, including explicit acceptance of any skipped entries.Same reader passes the range and reaches the verified healthy tail; record the accepted loss.
sleep 35
wm log readers "$WP_LOG"
wm segment probe "$WP_LOG" "$WP_SEG" --from-entry 51 --max-entries 100 \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"

The CLI probe confirms data readability; it does not automatically advance the application's reader. The closure is the same reader progressing plus application-level read success, not just a green command.
