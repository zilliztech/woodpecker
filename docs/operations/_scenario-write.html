Write Stalls

Find where append progress stops: application submission, node operations, buffering/flush, or quorum confirmation.

Plan: workload → operations → writer queues → LAC → recovery

StepCommandIntent
1node list/healthz; application append evidenceConfirm the app is submitting and the relevant replicas are reachable.
2ops list/show/statsLocate long-running append or flush operations without mistaking idle for a stall.
3logstore segments/segment-show/buffer/flush-queueIdentify the loaded writer and its buffer or flush bottleneck.
4logstore lac, twiceDetermine whether the ack quorum's durable frontier advances.
5Targeted fix, or reviewed fence-quorumRestore the failing stage, then verify application append success and LAC progress.

1. Confirm activity and reachability

w node list --strict
w node healthz "$WP_NODE"

First inspect the application's append attempts, returned errors and deadlines. Healthz answers process health, not write progress. One slow replica can be absorbed by the ack quorum; a cluster health color does not identify which segment stopped.

ResultInterpretation
All nodes reachable; no application append attemptsStart with workload/submission. There is no server-side write stall to prove yet.
App submits but no relevant operation reaches any replicaCheck the client's queue, RPC path and discovery/configuration before the node.
Replica unreachableCheck the address mapping/port-forward, pod state and network; then measure whether the remaining quorum still confirms writes.

2. Find the long-running operation

w ops list "$WP_NODE" --log "$WP_LOG_ID" --seg "$WP_SEG" \
  --longer-than 30000 -o json
w ops stats "$WP_NODE"
# Use an ID actually returned above:
w ops show "$WP_NODE" --op-id REAL_OP_ID
# Illustrative operation excerpt:
{"op_type":"logstore.add_entry", "op_id":"append-op-123",
 "log_id":42, "segment_id":7, "started_at":"..."}

Repeat on all quorum members. Compare IDs and ages across samples: the same append persisting is different from many short-lived appends. file.flush points at the flush path. Empty output is an instant snapshot; registry evictions and app work that never reached a node can be invisible.

OutputInterpretation
ops list has no matching items; stats in_use=0No tracked operation is in flight at this instant. With no workload this is normal; with pending client appends, check submission and other nodes.
The same OP_ID remains older than 30000ms in consecutive samplesA tracked operation is long-running. Use show to inspect its type, context and stage.
ops show returns TargetNotFoundThe operation finished or was evicted before the query. Refresh list rather than treating it as a missing segment.
stats old eviction total growsOld operations are being dropped from this bounded registry. Investigate alongside queues and errors; the cumulative total alone does not prove a current stall.

3. Inspect the loaded writer

w logstore segments "$WP_NODE" --log "$WP_LOG_ID"
w logstore segment-show "$WP_NODE" --log "$WP_LOG_ID" --seg "$WP_SEG"
w logstore buffer "$WP_NODE"
w logstore flush-queue "$WP_NODE"
# Buffer / flush-queue excerpts under load:
LOG:SEG  BUFFER_BYTES  BUFFER_ENTRIES
42:7     1048576       100

LOG:SEG  QUEUE_DEPTH  QUEUE_CAP
42:7     8            16

These are current occupancies, not latency measurements. Re-run while appends are outstanding: buffers draining and queue depth returning toward zero indicate progress; growing or persistently full queues need correlation with flush operations and backend errors. A single nonzero sample can be normal batching.

PatternMeaning / next check
Buffer/queue increases; flush operation does not finishInspect disk/object-storage errors, I/O latency and flush scheduling; correlate operation details.
No arriving appends and little queued workLikely upstream inactivity or a client/RPC issue; not evidence of a blocked flush.
segments shows only headers / segment-show is absentThese list loaded writer objects, not all persisted segments. Confirm the current segment and owner; do not infer no data.
One node behind; others advanceMeasure quorum confirmation. A lagging replica need not stall the application.

Read metadata when the writer registry is insufficient:

wm log scan "$WP_LOG" --from-segment "$WP_SEG" --to-segment "$WP_SEG" \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"

4. Compare LAC twice

wm logstore lac "$WP_LOG" "$WP_SEG"
sleep 10
wm logstore lac "$WP_LOG" "$WP_SEG"
NODE_ID                DURABLE_ENTRY  STATE
milvus-woodpecker-0     99             ok
milvus-woodpecker-1     99             ok
milvus-woodpecker-2     70             ok
quorum LAC: 99 (aq=2 of 3 nodes at or past it)
ResultInterpretation
LAC advancesDurability confirmation progresses. Investigate client completion/latency rather than assuming every append is blocked.
LAC unchanged while appends remain outstandingConfirmation is not advancing. Combine queues, errors and quorum-member evidence to locate the stage.
Fewer than AQ usable repliesLAC is unknown; restore reachability or replica availability. Unknown is not a confirmed smaller frontier.
no writerNode answered but has no loaded writer for this segment. Completed/Sealed metadata may still establish a boundary; check whether the application has rolled to a newer segment.

The CLI's --timeout is an HTTP deadline, not the application's append deadline. A 2s send budget does not guarantee an end-to-end append within 2s: confirmation, retries and rolling add time.

5. Restore the stage, then re-test append

Fix verified connectivity, storage or deployment failures first. A manual flush applies to a loaded writer and does not repair corrupted data:

w logstore force-flush "$WP_NODE" --log "$WP_LOG_ID" --seg "$WP_SEG"

If the intended recovery is to fence the old writer and let the application roll/reopen through its normal recovery path, review quorum impact first:

# Preview: no -y means no commit and exit code 7.
wm logstore fence-quorum "$WP_LOG" "$WP_SEG" \
  --reason "Reviewed recovery of stalled writer"
# After reviewing the selected nodes and impact:
wm logstore fence-quorum "$WP_LOG" "$WP_SEG" \
  --reason "Reviewed recovery of stalled writer" -y

Fencing can interrupt writes. The default WQ=3/AQ=2 needs two selected members to cross the interruption gate; fencing only one does not guarantee an interrupted quorum. StateConflict/insufficient reachable members means no verified quorum intervention, not success. Check fence-quorum for selection details.

6. Verify at the application and quorum

w ops list "$WP_NODE" --log "$WP_LOG_ID" --longer-than 30000
wm log scan "$WP_LOG" --mode quick \
  --bucket "$WP_BUCKET" --root-path "$WP_DATA_ROOT"
# Select the actual current segment if rolling changed it:
wm logstore lac "$WP_LOG" "$WP_SEG"

Require new application appends to succeed, the durable frontier to advance under workload, and old operations/queues to clear. A fence RPC or healthy pod alone is not the recovery result. If physical reads fail or CRC errors appear, switch to the corruption workflow.
