Helm Stack Walkthrough

Create a local Milvus + Woodpecker environment with its dashboards, alert evaluation and executable tests.

Prepare your environment

Use Docker, minikube, Helm 3, kubectl and Python 3.9+. The example expects at least 8 GiB available to the Docker VM, 8 host CPUs and about 20 GiB of provisioned storage. The Jupyter launcher requires Python 3.11+; connection discovery additionally uses the pinned PyYAML dependency. See the full prerequisites and pinned versions.

git clone https://github.com/zilliztech/woodpecker.git
cd woodpecker/deployments/milvus-full-stack-helm
./stack.sh help
python3 -m pip install -r scripts/requirements-connections.txt

The default profile/context is wp-ops-v0146, with namespace milvus-stack. start, stop and images target the minikube profile. Helm and kubectl operations explicitly target the selected Kubernetes context and namespace.

Deploy the stack

./stack.sh start
./stack.sh render
./stack.sh images
./stack.sh deploy
./stack.sh status

The public default uses Milvus v3.0.3 and Woodpecker v0.1.46. For the supplied private ARM64 Milvus development image, add --local-arm64 consistently to render, images and deploy; registry access or a preloaded image is required. The documented live validation used that ARM64 build; the public default image was not exercised in that run.

Milvus uses the official milvus-helm chart with three independent WP services. The support chart provides persistent etcd/MinIO, dashboards, PodMonitors and alert rules; kube-prometheus-stack provides the monitoring services.

Keep ports open in a separate terminal:

./stack.sh forward --wpcli

This includes the normal Milvus/monitoring forwards, one Admin endpoint per WP node and the example’s etcd endpoint. Matching existing forwards are reused, and Ctrl+C closes only the forwards started by this invocation. In another terminal, inspect the actual host addresses:

./stack.sh connections
./stack.sh connections --json

Only addresses marked forwarded have a matching local kubectl process and listening socket; proposed ports are not verified connections. WP Admin URL mappings support HTTP administration. The SDK’s advertised gRPC addresses have separate reachability requirements.

Run the first verification

./stack.sh smoke
# Allow two 15-second scrapes after the workload.
./stack.sh verify
./stack.sh alerts

smoke exercises inserts, queries and search through Milvus. verify checks the five Milvus and three WP scrape targets, core workload counters and provisioned dashboard queries. alerts checks rule health and the Alertmanager path. A nonzero exit needs investigation; a running Pod alone does not establish that this chain works.

Follow the Jupyter guide

./stack.sh notebook

Open the authenticated loopback URL printed by Jupyter and select notebooks/full-stack-walkthrough.ipynb. The guide covers deployment, dashboards, workloads, write performance, alerts and evidence. Review its configuration cell: it defaults to the supplied ARM64 build, so set USE_LOCAL_ARM64=False for the public image. Stop/clear cells are disabled by default.

Pause, resume or reset

PairBehavior
stop / startPause/resume the local minikube cluster, preserving the deployments and data. Reopen forwards after restarting.
deploy / clearInstall/upgrade the Helm releases, or uninstall them and delete their PVC data. The namespace, shared CRDs, minikube profile and local evidence remain.
./stack.sh clear deletes this stack’s Milvus/WP, etcd/MinIO and monitoring PVC data. Use stop when you want to retain the deployed data for another session.

For existing clusters, additional Helm values and upgrade/storage details, use the deployment reference. Continue with monitoring and alerts or wpcli operations.
