Helm Stack Walkthrough

Deploy and operate Milvus + Woodpecker on your existing Kubernetes cluster using reviewable Helm and kubectl commands.

Prepare an existing Kubernetes context

Use configured kubectl, Helm 3 and Python 3.9+. Kubernetes, its nodes, credentials, StorageClass and registry access are managed outside this tool. This applies equally to a shared cluster, kind or local minikube. Docker is optional for offline rule tests; Jupyter needs Python 3.11+.

git clone https://github.com/zilliztech/woodpecker.git
cd woodpecker/deployments/milvus-full-stack-helm
python3 -m pip install -r scripts/requirements-connections.txt
kubectl config current-context
kubectl version
./stack.sh help

The default context is kubectl’s current context; override it with --context NAME or CONTEXT. The default namespace is milvus-stack, configurable with --namespace / NAMESPACE. An unavailable context produces configuration guidance; stack.sh never creates, starts, stops or deletes Kubernetes.

Review, then deploy

./stack.sh render
./stack.sh images                       # Image inventory only
./stack.sh deploy                       # Preview native commands
./stack.sh deploy -x                    # Execute the reviewed resource operations
./stack.sh status

Resource changes, workload writes and port forwards are previewed by default; -x executes them. Planning may read the cluster and save local values/manifests; it does not change resources. Read-only status and local rendering remain available without -x. Printed Helm/kubectl commands include the explicit target and can be copied directly.

A first deployment contains only Milvus, three independent WP services and persistent etcd/MinIO. It wraps the official Milvus Helm chart and needs no monitoring CRDs. Public defaults use Milvus v3.0.3 and WP v0.1.46. Add --local-arm64 to render/images/deploy for the supplied private ARM64 build; prepare its image access outside the stack.

Add optional components later

./stack.sh addons-deploy --with prometheus,grafana   # Preview
./stack.sh addons-deploy --with prometheus,grafana -x
./stack.sh addons-deploy --with alertmanager -x
./stack.sh addons-deploy --with jaeger,loki -x
./stack.sh addons-status

Use --with all for the complete observability example. Loki includes Alloy for log collection. Addon changes preserve live core overrides and previously selected components; changing Jaeger selection updates trace configuration and rolls Milvus/WP. See component dependencies and lifecycle.

Discover and open endpoints

./stack.sh forward --wpcli               # Preview native port-forward commands
./stack.sh forward --wpcli -x            # Keep running in a separate terminal
./stack.sh connections
./stack.sh connections --json

Only installed services are forwarded. --wpcli also includes per-node WP Admin and tenant etcd. Matching existing forwards are reused, and Ctrl+C closes only those started by this invocation. Only addresses marked forwarded are verified local connections; Admin HTTP forwarding does not establish SDK advertised-gRPC reachability.

Run the first verification

./stack.sh smoke -x
# Allow two 15-second scrapes when Prometheus is installed.
./stack.sh verify
./stack.sh alerts

Smoke writes real data and checks query/search. Verify requires Prometheus, with Grafana provisioning checks when selected. The alert flow uses Prometheus + Alertmanager. Core-only perf still checks writes/reads and explicitly marks absent metrics/alerts as skipped. A running Pod alone does not establish a healthy chain.

Follow the Jupyter guide

./stack.sh notebook

Open the authenticated loopback URL and select notebooks/full-stack-walkthrough.ipynb. It selects the complete observability profile. EXECUTE=False previews by default; set EXECUTE=True after reviewing the target, images, ports and load. The guide never manages Kubernetes and keeps stop/clear cells disabled by default.

Pause/resume workloads or remove the deployment

CommandEffect with -xData boundary
deployInstall/upgrade Helm releases on the existing cluster and run the selected stack.Retain PVCs and existing addons.
stopRecord replica state and pause this stack’s workloads using native scale/patch/wait commands.Retain Helm releases/PVCs; memory/ephemeral history may disappear.
startRestore the replica counts saved by stop and wait for rollouts.Does not install a missing stack or start Kubernetes.
clearUninstall stack releases and delete their PVC data.Retain Kubernetes, namespace, shared CRDs and local evidence.
addons-deploy / addons-clearAdd components / remove selected components and their data.Retain the core deployment.
 
./stack.sh stop                  # Review only
./stack.sh stop -x               # Pause workloads; leave Kubernetes running
./stack.sh start -x              # Restore saved workload replicas
./stack.sh forward --wpcli -x
./stack.sh clear                 # Review the deletion plan
# ./stack.sh clear -x            # Executes deletion of releases AND PVC data

Stop state is stored in the namespace ConfigMap milvus-full-stack-lifecycle, so resume does not depend on one machine. Prometheus/Alertmanager are scaled through their Operator resources, and Alloy’s DaemonSet uses a reversible scheduling selector. Resume before changing Helm releases. Unsafe scale-down PVC retention policies and active autoscalers are reported before any write.

Continue with metrics, logs, traces and alerts or wpcli operations. See the separate local Kubernetes preparation example if you choose minikube.
