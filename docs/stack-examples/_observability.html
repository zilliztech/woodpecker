Metrics, Logs, Traces & Alerts

Follow the same workload from Milvus through the WP client and servers, then check that the operational signals reach your dashboards and Alertmanager.

Select the signals you need

./stack.sh addons-install --with prometheus,grafana,alertmanager -x
./stack.sh addons-install --with jaeger,loki -x
./stack.sh forward --wpcli -x

Each component is optional and can be added after the core deployment. Grafana displays data from the selected backends; it does not store their metrics, logs or spans. Existing forwards need a new invocation to include newly installed services. See independent selection and removal.

Start with an E2E operational dashboard

For a specific symptom, use the E2E dashboards: Write / Append, WAL Read / Consume, Flush / Checkpoint, or Search / Query. They group the metrics by processing step and include investigation guidance. Use the three component reference dashboards below for deeper inspection.

Check the monitoring chain

./stack.sh smoke -x
# Wait at least 30 seconds for scrapes.
./stack.sh verify

The verification report is saved to .local/verification.json. It checks target health, positive application/WP workload metrics, dashboard provisioning and query compatibility. Some panels need a particular operation or enough rate-window history before showing finite samples. An empty panel is an investigation prompt, not proof that the corresponding operation is healthy or broken.

If application writes succeed but WP activity is missing, check the deployed Milvus configuration, metric families and label selection before drawing a conclusion about the write path. The dashboard source record documents the Milvus production export and adaptations of the WP Kubernetes templates.

Inspect individual request traces

When selected, the stack deploys jaegertracing/all-in-one:1.53.0 and exports Milvus and WP spans over OTLP. Open Jaeger directly, or select the provisioned Jaeger datasource in Grafana Explore.

./stack.sh traces
./stack.sh traces-smoke -x
# Strict E2E coverage: fails on disconnected request paths.
TRACES_REQUIRE_E2E=1 ./stack.sh traces-smoke -x

The smoke probe writes 100 vectors and verifies Strong query/search, then saves exact request trace IDs, client latency and raw spans. Normal perf records also contain sampled trace links. The supplied image currently connects query/search through SN and segcore, while its user Insert trace does not continue into SN/WP. Separate WP exporter activity is not proof of an E2E write trace; the report explicitly records this gap as partial.

Full sampling favors small diagnostic runs and changes system overhead. Lower both server and workload sampling for sustained tests. Jaeger history is bounded and in memory, so save evidence before eviction or restart. See tracing setup, interpretation and known gaps.

Search real Pod logs

Loki stores compressed log chunks and label indexes on a 4 GiB PVC, with a 24-hour retention policy. Alloy tails this namespace’s container logs through the Kubernetes API. In Grafana Explore, select Loki and query {namespace="milvus-stack"}, then filter by Pod or text. When Jaeger is also selected, recognized trace IDs link to its trace view.

./stack.sh logs
./stack.sh logs-smoke -x

The smoke test runs a small Milvus write/query/search workload, finds its unique collection marker in the actual Proxy log and requires that marker to arrive through Alloy into Loki. It saves .local/logging-smoke.json. Collection is bounded by source-log retention and collector availability; see storage, queries and limitations.

Inspect and test alerting

Prometheus evaluates the 31 reference WP rules covering resource pressure, failures, scaling signals and client behavior. Firing alerts are sent to Alertmanager for grouping and inhibition. The default local-only receiver lets you inspect alerts in the Prometheus and Alertmanager UIs without sending email or other external notifications.

./stack.sh alerts-test   # Offline rule behavior checks; uses Docker.
./stack.sh alerts        # Live rule/receiver/AM discovery checks.
./stack.sh alerts-smoke  -x # Temporary synthetic firing/recovery/inhibition checks.

The synthetic check verifies the alerting path and removes its temporary resources. It does not create each underlying disk, object-store or quorum failure, and it does not prove that every production threshold is suitable for your workload. See the rule catalog, investigation guidance and validation details.

When external notification is needed, use the optional SMTP configuration example with your relay and credentials. Optional Mailpit testing captures email locally. Neither profile is enabled by default.

Adopt the signals in an existing deployment

  1. Match Prometheus discovery selectors and labels to your Milvus and WP Pods. Confirm the exporters expose the metric families used by each query.
  2. Adapt Grafana data-source references, namespace/instance variables and dashboard time windows.
  3. Set alert thresholds and hold periods from your workload, capacity and recovery expectations; configure your Alertmanager receiver.
  4. Exercise a known workload and a controlled alert-path test, then preserve evidence showing which checks passed and which signals remain untested.

Use wpcli to inspect the specific node, log or metadata behind a symptom, and the experiment workflow to compare behavior before and after an improvement.
