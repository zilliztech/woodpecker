E2E Testing & Optimization

Use a repeatable workload and its operational evidence to find gaps, investigate bottlenecks and evaluate a change.

Establish a working baseline

With the stack and forwards running, start with the integrated acceptance path:

./stack.sh acceptance -x

This always runs a Milvus insert/query/search workload, explicitly flushes the collection and verifies its complete row count and search afterward, then collects evidence. Even a small workload exercises persistence metrics without waiting for automatic flush thresholds. It also tests the selected backends: Prometheus rules and metrics, Grafana dashboards, Jaeger trace coverage, Loki log delivery and the Prometheus + Alertmanager firing/recovery/inhibition path. External email is not enabled. Each stage must succeed; keep the resulting reports if one fails so you can inspect that stage. Default trace verification reports known gaps separately; use strict E2E mode when a complete connected path is required.

Run a bounded write experiment

./stack.sh perf -x

The default run uses a 5-second warm-up, a 60-second measurement window, two workers and a total target of five 100-vector insert requests per second. It then waits 35 seconds for observation. It creates and retains its own collection, checks live read/query/search results and records acknowledged throughput, errors and insert latency.

PERF_DURATION=300 PERF_CONCURRENCY=4 PERF_BATCH_SIZE=200 PERF_RPS=10 ./stack.sh perf -x

This example raises the requested load; achieved throughput depends on the workload generator and stack. Compare one change at a time with the same images, resources and parameters. REST transport and port-forward overhead are part of the measured latency, and successful live reads do not prove durability through a crash.

Follow the evidence

Each performance run writes a unique directory under .local/perf/, including:

ArtifactUse
summary.md, report.jsonResults, parameters, correctness checks, missing signals, failures and workload/collection observations.
requests.jsonlInsert attempts, row-ID ranges, timestamps, latency and errors.
signals.jsonl, metric-*.jsonMetric/alert snapshots and exact queries over the run’s time range.
pods.json, events.txt, logsComponent images/resources, Kubernetes events and bounded component logs.

Start from failed writes or correctness checks, then compare Milvus mutation latency, WP client append/queue behavior, server RPC/flush latency and storage/resource signals. Use node/log identities and timestamps to narrow the wpcli and log investigation. Missing lazy error counters or idle histograms are coverage gaps until the corresponding behavior is exercised.

For a wider snapshot, run ./stack.sh collect. The detailed performance guide explains gates, artifact limits and interpretation. Review logs before sharing evidence.

Turn an observation into an improvement

  1. Record the symptom and baseline. Keep the workload parameters, timestamps, selected instance and observed result.
  2. Locate the affected stage. Distinguish load-generator delay, Milvus processing, WP client queues, server work and object storage.
  3. Close the relevant gap. Improve a metric, query, alert, runbook or configuration based on that evidence.
  4. Rerun and compare. Verify application results, operational checks and the new signal under the same conditions.

Use the same approach on your own Milvus + WP deployment after adapting endpoints, labels, permissions and workload limits. Treat a local result as evidence for the measured configuration, then validate the change on the target environment.

Validate diagnosis through a controlled slowdown

The deployed CLI acceptance guide provides a separate, explicitly opted-in scenario: normal writes and strong queries, controlled producer admission throttling, then recovery. It reuses the bounded workload and existing wpdiag milvus append, milvus query and run commands. It requires a dedicated disposable namespace, a compatible Milvus management API and Prometheus; no WebUI is required.

The harness records user latency, throughput, correctness, exact metric windows and source/stage findings, compares standalone and composed diagnoses, and verifies configuration restoration. With an optional current wpcli snapshot, it checks that a recovered current state does not clear the retained historical incident. Missing or inconclusive completion metrics cannot pass as normal traffic. A failed or non-reproducing fault remains a failed receipt.

Read the preparation and recovery instructions before executing: this harness creates its own collection and temporarily changes deployment-wide admission controls. It never manages the Kubernetes cluster lifecycle. Plain wpdiag commands remain read-only. This covers the first CLI subset of the original #458; remaining validation is tracked through #450 and focused follow-ups.

Validate new-scanner consumption and initial visibility

The separate consume acceptance guide covers #484: working writes and Strong queries, intentional idle, an explicitly paused new scanner, and recovery. It uses the existing Prometheus/consume/integrated commands without Jaeger, Loki, native metadata or WebUI dependencies.

The native pause control is checked at scanner startup; it does not stop an already-running reader. The test creates only its own collections and contrasts bounded initial-visibility query timeouts with an existing collection that remains queryable. A collection still Loading is not presented as an already-loaded slow reader. Continuously sampled pause with zero pending bytes remains an observation, not a fabricated downstream or disk-pressure conclusion.

The harness journals and restores the exact setting/override absence, verifies every acknowledged ID and vector search after recovery, compares standalone/composed results, and preserves the original historical interval. Review its offline plan and dedicated-namespace opt-in before adding --execute. See the deployed validation receipt for actual builds, observations and limits.

Validate loaded query/search consistency

The loaded query/search consistency acceptance guide covers #486: baseline and idle, actual TSafe waits from a bounded server-derived Customized guarantee timestamp, paired Strong controls, and normal-request recovery. The collection stays Loaded; no scanner, Pod or shared configuration is paused. This request control is distinct from a Strong-query production incident.

The deployed receipt records successful exact query/search results, default-policy visibility findings, historical replay and standalone/composed lineage. The protocol helper is isolated from production dependencies. Use the offline plan and dedicated-namespace opt-in before execution.

Validate object-store CPU slowdown and persistence recovery

The separate persistence acceptance guide covers #488: working sync completions, intentional idle, bounded in-place CPU throttling of PVC-backed MinIO, and normal-workload recovery. The harness journals controller/claim ownership and original CPU resources, respects the deployment's existing flush quota, restores resources before exact-ID/search checks and owned-data cleanup, and compares standalone/integrated historical findings at unchanged policy.

Only an explicitly opted-in disposable namespace may run this deployment-wide dependency fault. Sync completion includes upload and callbacks; pending tasks include queued and executing work. Idle checkpoint age, a seen TimeTick and slow completion timers do not prove physical disk/fsync failure or crash durability. The deployed receipt records the selected builds, failed attempts, actual contrast and limits.

Future operational chapters

This collection can grow with controlled restart/recovery drills, read/write stall investigations, disk/object-store pressure scenarios, scaling/capacity comparisons and optimization experiments. These fault scenarios are not automatically exercised by the current performance test.

Each new chapter should provide a reproducible starting state, bounded trigger, expected metrics and alerts, wpcli/log investigation, recovery procedure and application-level verification. Structured reports and meaningful exit status make those chapters reusable by local AI agents as well as people. Autonomous orchestration remains a future addition.
