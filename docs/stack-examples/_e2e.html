E2E Testing & Optimization

Use a repeatable workload and its operational evidence to find gaps, investigate bottlenecks and evaluate a change.

Establish a working baseline

With the stack and forwards running, start with the integrated acceptance path:

./stack.sh acceptance -x

This always runs a Milvus insert/query/search workload, explicitly flushes the collection and verifies its complete row count and search afterward, then collects evidence. Even a small workload exercises persistence metrics without waiting for automatic flush thresholds. It also tests the selected backends: Prometheus rules and metrics, Grafana dashboards, Jaeger trace coverage, Loki log delivery and the Prometheus + Alertmanager firing/recovery/inhibition path. External email is not enabled. Each stage must succeed; keep the resulting reports if one fails so you can inspect that stage. Default trace verification reports known gaps separately; use strict E2E mode when a complete connected path is required.

Run a bounded write experiment

./stack.sh perf -x

The default run uses a 5-second warm-up, a 60-second measurement window, two workers and a total target of five 100-vector insert requests per second. It then waits 35 seconds for observation. It creates and retains its own collection, checks live read/query/search results and records acknowledged throughput, errors and insert latency.

PERF_DURATION=300 PERF_CONCURRENCY=4 PERF_BATCH_SIZE=200 PERF_RPS=10 ./stack.sh perf -x

This example raises the requested load; achieved throughput depends on the workload generator and stack. Compare one change at a time with the same images, resources and parameters. REST transport and port-forward overhead are part of the measured latency, and successful live reads do not prove durability through a crash.

Follow the evidence

Each performance run writes a unique directory under .local/perf/, including:

ArtifactUse
summary.md, report.jsonResults, parameters, correctness checks, missing signals, failures and workload/collection observations.
requests.jsonlInsert attempts, row-ID ranges, timestamps, latency and errors.
signals.jsonl, metric-*.jsonMetric/alert snapshots and exact queries over the run’s time range.
pods.json, events.txt, logsComponent images/resources, Kubernetes events and bounded component logs.

Start from failed writes or correctness checks, then compare Milvus mutation latency, WP client append/queue behavior, server RPC/flush latency and storage/resource signals. Use node/log identities and timestamps to narrow the wpcli and log investigation. Missing lazy error counters or idle histograms are coverage gaps until the corresponding behavior is exercised.

For a wider snapshot, run ./stack.sh collect. The detailed performance guide explains gates, artifact limits and interpretation. Review logs before sharing evidence.

Turn an observation into an improvement

  1. Record the symptom and baseline. Keep the workload parameters, timestamps, selected instance and observed result.
  2. Locate the affected stage. Distinguish load-generator delay, Milvus processing, WP client queues, server work and object storage.
  3. Close the relevant gap. Improve a metric, query, alert, runbook or configuration based on that evidence.
  4. Rerun and compare. Verify application results, operational checks and the new signal under the same conditions.

Use the same approach on your own Milvus + WP deployment after adapting endpoints, labels, permissions and workload limits. Treat a local result as evidence for the measured configuration, then validate the change on the target environment.

Validate the current Woodpecker diagnostic tool

The current workflow is tracked in #503: wp CLI atomic Metrics/Trace checks, scenario summaries, native Operations, Command Explorer and optional supplied-report Agent analysis. Use wp diag and wp webui; the old wpdiag execution surface is retired.

make wpcli
python3 cmd/wpdiag/tests/workspace_acceptance.py
python3 cmd/wpdiag/tests/prometheus_smoke.py
python3 cmd/wpdiag/tests/jaeger_smoke.py

Browser acceptance uses bounded HTTP fixtures and a fake Agent; source smoke tests use isolated temporary Prometheus/Jaeger containers. These are separate from real deployment receipts. Record the actual image/build, interval, scope and source coverage when checking the stack. Missing samples, idle traffic and an incomplete Trace query are not proof of health.

Confirm WP runtime observations

Use current WP Metrics/Admin commands and explicitly scoped metadata to confirm a suspected WAL problem. The earlier native acceptance guide records its bounded service fixture and limits. Do not run fault-injection harnesses against a shared deployment. Existing metadata views/checks are native operations, not a new dynamic metadata diagnosis subsystem.
