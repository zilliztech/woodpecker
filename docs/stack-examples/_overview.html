Milvus–Woodpecker Stack Examples

Install, observe and operate Milvus with Woodpecker through a complete, open-source example stack.

Why this stack exists

A running Milvus + Woodpecker deployment is easier to operate when application behavior, WAL health, resource pressure and alerts can be examined together. Users who have not yet deployed monitoring or operational tools can start here with a working example, then adapt its configuration and investigation methods to their own instances.

The default deployment contains Milvus and independent Woodpecker services with persistent dependencies. Add Prometheus, Grafana, Alertmanager, Jaeger and Loki/Alloy independently, and use wpcli for operations. A real Milvus workload exercises its WP client and the WP servers, so the example explains what to observe along the write path and how to investigate it.

Exercise the write pathMilvus workload → Milvus + WP client → WP services → object storage
Observe and investigatePrometheus → Grafana + Alertmanager · wpcli → WP services and client metadata

What you can do today

Install with HelmInstall Milvus, three WP service replicas and persistent dependencies on existing Kubernetes; add observability independently. Preview native commands before executing. Follow an E2E symptomUse four ordered dashboards for writes, WAL consumption, persistence and search/query; follow each step’s metrics and investigation guidance. Operate with wpcliDiscover reachable endpoints, select a WP service context and explicitly connect to a Milvus instance’s WP client metadata. Run a repeatable experimentInsert and read data, measure writes, inspect correlated metrics and logs, collect evidence and repeat after a change.

The runnable example lives in deployments/milvus-full-stack-helm/. It uses the official Milvus Helm chart, a small support chart and pinned monitoring components. Values files, dashboard JSON, alert rules, workload scripts and the notebook are included in the repository.

The monitoring and alerting guide connects these E2E views with the Milvus/WP reference dashboards, scrape verification and Alertmanager.

One operational feedback loop

  1. Install a known environment. Record chart/image versions, namespace, resource settings and connection targets.
  2. Run a real workload. Verify Milvus inserts, primary-key queries and vector search, then establish a small write-performance baseline.
  3. Check the whole chain. Compare application results with Milvus/WP metrics, dashboards, alerts, wpcli state and logs for the same time window.
  4. Improve and repeat. Investigate failures or missing signals, change one setting or instrument, and rerun the same scenario.

Commands return exit status and save structured artifacts so humans and local AI agents can follow the same loop. The current stack provides these building blocks; autonomous investigation and optimization are future extensions.

Apply the examples to your own instances

Start with a local stack to learn the expected signals and command output. For an existing Milvus + WP instance, adapt scrape selectors, dashboard variables, alert thresholds and notification routes to its topology and workload. Use that instance’s reachable WP Admin URLs and its own etcd namespace and storage paths when configuring wpcli.

Distinguish the shared WP service cluster from the metadata managed by a particular Milvus instance’s WP client. The two connection scopes are explicit in the generated configuration and operations examples.

The supplied resource sizes, single-node dependencies and example credentials are for a development environment. Use your deployment’s availability, access and storage requirements when adopting the configurations. Performance results from this local setup describe that setup.
