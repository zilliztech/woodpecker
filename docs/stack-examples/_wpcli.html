wpcli Operations in the Stack

Connect to the WP service cluster, attach the selected Milvus instance’s WP client metadata, and use both views during an investigation.

Prepare wpcli and local access

Install wp using the CLI setup guide, and check wp version and wp --help. The noninteractive examples work with the established operations; interactive wp shell requires a source build containing the shell addition and is not part of v0.1.47.

Run the following from deployments/milvus-full-stack-helm/, with the stack deployed and the connection-discovery Python dependency installed:

# Keep this running in a separate terminal.
./stack.sh forward --wpcli -x
./stack.sh connections
./stack.sh connections --wpcli-config > .local/wpcli.yaml
export WOODPECKER_CLI_CONFIG="$PWD/.local/wpcli.yaml"
wp ctx view

This creates a separate stack-local file. Your personal ~/.woodpecker/cli.yaml is unchanged. Export requires working WP Admin forwards; metadata readiness is reported separately. Re-run discovery after changing the deployment or restarting forwards.

Understand the two connection scopes

ScopeConfigurationPurpose
WP service clustercli.yaml: Admin endpoint, per-node Admin URL mappings and Kubernetes context/namespace.Inspect WP nodes and their runtime state. Select this connection with --context.
Milvus instance WP client metadataSeparate etcd endpoint and full metadata prefix; bucket/root path when an operation needs the storage identity.Inspect metadata managed by this Milvus instance’s WP client. Supply explicit flags or attach it inside the shell.

--wpcli-config puts the second scope in an independent comment section, with a copyable connect command. It does not put etcd, metadata-prefix or storage settings into the generated ctx.

In the default example, etcd is reachable at 127.0.0.1:32379 and the complete metadata prefix is full-stack/woodpecker, derived from Milvus’s etcd.rootPath and woodpecker.meta.prefix. The bucket is milvus-bucket; the WP WAL root is milvus/wp, including the /wp suffix added by the Milvus WAL adapter.

Use the discovered values for your instance. A shared WP service cluster can serve different clients; selecting its ctx alone does not identify which client metadata you intend to inspect.

Inspect nodes and metadata

# Service-level inspection uses only the WP context.
wp --context wp-ops-v0146/milvus-stack node list

# Select this Milvus instance's metadata explicitly.
wp --context wp-ops-v0146/milvus-stack \
  --etcd 127.0.0.1:32379 --meta-prefix full-stack/woodpecker \
  meta log list

The first result describes service nodes. The second lists logical logs in the chosen client metadata namespace. Keep actual log/node/segment identities from these results when following a diagnosis workflow; sample IDs from another environment will refer to different data.

Keep an interactive operational session

With a binary whose help lists shell, start a session using the generated context. Without --context, an interactive terminal offers the configured contexts for selection.

wp shell --context wp-ops-v0146/milvus-stack

Inside the shell, attach the Milvus instance’s WP client metadata explicitly:

connect milvus-stack --etcd 127.0.0.1:32379 --meta-prefix full-stack/woodpecker --bucket milvus-bucket --root-path milvus/wp
status --check
node list
meta log list

status --check verifies Admin and etcd access for the current session. These connection checks establish reachability; use a workload and the relevant log/data checks to establish application progress and readability.

Plan an integrated diagnosis

wpdiag run selects the existing source modules and stage assessors through one bounded, headless command. Begin with the plan to see module/profile versions, source connections, windows and budgets before collecting evidence. Configure only the sources you need; the example stack is optional. See the integrated diagnosis guide and supported matrix.

make wpcli wpdiag
bin/wpdiag run --list
bin/wpdiag run --config wpdiag.yaml --scope e2e --flow write --plan
bin/wpdiag run --config wpdiag.yaml --scope e2e --flow write \
  --sources prometheus,wpcli --stages append \
  --window 30s --budget 1m --progress -o json > run.json

Write auto plans select append/persistence metrics; read plans select consume/query metrics. Native WP and optional trace/log source overviews keep their own declared coverage. Choose exact sources/modules and source-local connections when needed. Explicitly selected unavailable sources produce partial/error status; completed execution is not a cluster-health verdict. Reports retain original finding IDs, evidence, contradictions, uncertainties and next checks.

# Substitute the incident interval and your own named connections.
bin/wpdiag run --config wpdiag.yaml --scope e2e --flow write \
  --sources prometheus,wpcli --stages append --current-native \
  --connections prometheus=metrics,wpcli=native \
  --mode historical --from 2026-10-26T01:00:00Z --to 2026-10-26T01:05:00Z -o json

Historical auto plans omit current native state. --current-native adds a separately labeled snapshot, which cannot disprove a historical incident. Matching observed trace IDs, deployment binding and actual event times can associate retained Jaeger/Loki evidence. Missing channel/WP-client metadata mappings remain explicit; same-time anomalies and matching numeric IDs are not joined. The CLI and future WebUI share the runner's run/cancel/progress/report API; this version introduces no WebUI server.

Use wpcli with the dashboards

For slow query/search, the independent wpdiag milvus query command uses a Prometheus connection to assess Proxy completion, visibility waiting, scheduling, execution/loading and result return. It preserves source evidence and distinguishes persistent ready backlog from recovery; TSafe or query delay alone does not implicate WP. See the query-stage guide, metric catalog and evidence limits.

bin/wpdiag milvus query --list
# Configure the named Prometheus connection and use your actual workload interval.
bin/wpdiag milvus query --config wpdiag.yaml --connection stack \
  --scope milvus --mode historical \
  --from 2026-10-26T01:00:00Z --to 2026-10-26T01:05:00Z

For WAL consumption or visibility lag, use wpdiag milvus consume. Its five groups cover read modes, separately observed WP retrieval, scanner buffers, subscription/dispatch and consumer processing. It distinguishes sampled pressure from recovery and normal blocking ReadNext/EOF; idle or missing series do not prove a stall. The initial path uses Prometheus only and shows missing client-metadata mappings explicitly. See the consume-stage guide, metric catalog and evidence limits.

bin/wpdiag milvus consume --list
# Substitute the retained interval for your workload.
bin/wpdiag milvus consume --config wpdiag.yaml --connection stack \
  --scope e2e --mode historical \
  --from 2026-10-26T01:00:00Z --to 2026-10-26T01:05:00Z -o json

Source builds also provide an independent wpdiag binary for bounded diagnostic reports. Build it with make wpcli wpdiag, inspect bin/wpdiag capabilities, and configure a named connection referring to the generated wpcli context and cli.yaml. See the wpdiag setup and examples.

# From the repository root, after preparing wpdiag.yaml with your connection.
bin/wpdiag wpcli diagnose --config wpdiag.yaml --connection local \
  --scope wp --flow write --window 30s --interval 1s --budget 1m -o json
bin/wpdiag wpcli diagnose --config wpdiag.yaml --connection local \
  --scope wp --flow read --stage wal_read --mode snapshot -o json

The native module imports WP runtime evidence from wp diagnose; it does not require Prometheus, Jaeger or Loki. Completion is not a health verdict, snapshots cannot establish sustained stalls, and current ops cannot answer historical questions. Source-specific and integrated Milvus E2E diagnosis have separate boundaries; unimplemented combinations return an explicit unsupported result.

The independent wpdiag trace diagnose command (alias wpdiag jaeger diagnose) reads Jaeger using its own connection and exact service bindings. It reports suspicious spans and partial/connected observed stages for WP, Milvus or source-only E2E reads/writes. An Insert trace missing SN/WP spans remains partial; normal ReadNext waiting, async work and overlapping spans are not converted into a serial latency total. See the Jaeger setup, profiles and evidence limits.

# Configure sources.trace.connections.stack in wpdiag.yaml; replace the ID.
bin/wpdiag trace diagnose --config wpdiag.yaml --connection stack \
  --scope e2e --flow write --mode snapshot --trace-id YOUR_TRACE_ID -o json

For a retained metric interval, the separate wpdiag prometheus diagnose command works using only a Prometheus connection. It has WP, Milvus and source-only E2E read/write profiles that report observed latency bounds, throughput changes, exported admission pressure and evidence gaps. See the Prometheus setup, metric catalog and interpretation guide. These profiles assess component populations independently; use the stage commands or integrated runner to compose the available stage assessments while retaining their evidence limits.

# Configure a Prometheus connection named stack and use your workload's UTC interval.
bin/wpdiag prometheus diagnose --config wpdiag.yaml --connection stack \
  --scope e2e --flow write --mode historical \
  --from 2026-10-25T08:00:00Z --to 2026-10-25T08:05:00Z -o json

Start from the symptom and the test’s time window. Use in-flight operations and writer runtime for slow writes, log progress and segment diagnosis for stalled progress, and metadata inspection when coordinator state needs examination.

The write-stall, read-stall and data-corruption guides explain the evidence and verification needed for each investigation. Begin with their read-only inspection steps and choose any repair from the observed cause and consequences.

The independent wpdiag loki diagnose command reads retained WP/Milvus logs using its own Loki connection. Select WP, Milvus or source-only E2E reads/writes. Findings include known message excerpts, event lineage and exact LogQL/windows; no-match remains inconclusive. Cross-component association requires an actual shared request/trace identity. See the Loki configuration, supported patterns and evidence limits.

# Configure sources.loki.connections.stack using the Alloy namespace/cluster labels.
bin/wpdiag loki diagnose --config wpdiag.yaml --connection stack \
  --scope e2e --flow write --window 30s --budget 1m -o json

For slow inserts, wpdiag milvus append assesses Proxy preparation/completion, producer quota/routing, SN WAL/interceptors and, with --scope e2e, separate WP append/flush/disk context. It reuses Prometheus source findings and reports concrete steps, evidence and next checks. Internal quantiles are never subtracted to invent waiting time; WP evidence stays unassociated until an authoritative client metadata mapping exists. See the append-stage catalog, setup and interpretation limits.

bin/wpdiag milvus append --list
bin/wpdiag milvus append --config wpdiag.yaml --connection stack \
  --scope e2e --window 30s --budget 1m -o json

For persistence lag, wpdiag milvus persistence uses an independent Prometheus connection to assess growing pressure, sync scheduling/recovery, execution/upload timing and checkpoint advancement. A flusher-seen TimeTick is not a durable checkpoint; idle checkpoint age is not a stall. E2E WP flush/offload is shown as a parallel path with explicit mapping gaps. See the persistence-stage hypotheses, configuration and evidence limits.

bin/wpdiag milvus persistence --list
bin/wpdiag milvus persistence --config wpdiag.yaml --connection stack \
  --scope e2e --window 30s --budget 1m -o json
