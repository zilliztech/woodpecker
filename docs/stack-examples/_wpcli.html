wpcli Operations in the Stack

Connect to the WP service cluster, attach the selected Milvus instance’s WP client metadata, and use both views during an investigation.

Prepare wpcli and local access

Install wp using the CLI setup guide, and check wp version and wp --help. The noninteractive examples work with the established operations; interactive wp shell requires a source build containing the shell addition and is not part of v0.1.47.

Run the following from deployments/milvus-full-stack-helm/, with the stack deployed and the connection-discovery Python dependency installed:

# Keep this running in a separate terminal.
./stack.sh forward --wpcli
./stack.sh connections
./stack.sh connections --wpcli-config > .local/wpcli.yaml
export WOODPECKER_CLI_CONFIG="$PWD/.local/wpcli.yaml"
wp ctx view

This creates a separate stack-local file. Your personal ~/.woodpecker/cli.yaml is unchanged. Export requires working WP Admin forwards; metadata readiness is reported separately. Re-run discovery after changing the deployment or restarting forwards.

Understand the two connection scopes

ScopeConfigurationPurpose
WP service clustercli.yaml: Admin endpoint, per-node Admin URL mappings and Kubernetes context/namespace.Inspect WP nodes and their runtime state. Select this connection with --context.
Milvus instance WP client metadataSeparate etcd endpoint and full metadata prefix; bucket/root path when an operation needs the storage identity.Inspect metadata managed by this Milvus instance’s WP client. Supply explicit flags or attach it inside the shell.

--wpcli-config puts the second scope in an independent comment section, with a copyable connect command. It does not put etcd, metadata-prefix or storage settings into the generated ctx.

In the default example, etcd is reachable at 127.0.0.1:32379 and the complete metadata prefix is full-stack/woodpecker, derived from Milvus’s etcd.rootPath and woodpecker.meta.prefix. The bucket is milvus-bucket; the WP WAL root is milvus/wp, including the /wp suffix added by the Milvus WAL adapter.

Use the discovered values for your instance. A shared WP service cluster can serve different clients; selecting its ctx alone does not identify which client metadata you intend to inspect.

Inspect nodes and metadata

# Service-level inspection uses only the WP context.
wp --context wp-ops-v0146/milvus-stack node list

# Select this Milvus instance's metadata explicitly.
wp --context wp-ops-v0146/milvus-stack \
  --etcd 127.0.0.1:32379 --meta-prefix full-stack/woodpecker \
  meta log list

The first result describes service nodes. The second lists logical logs in the chosen client metadata namespace. Keep actual log/node/segment identities from these results when following a diagnosis workflow; sample IDs from another environment will refer to different data.

Keep an interactive operational session

With a binary whose help lists shell, start a session using the generated context. Without --context, an interactive terminal offers the configured contexts for selection.

wp shell --context wp-ops-v0146/milvus-stack

Inside the shell, attach the Milvus instance’s WP client metadata explicitly:

connect milvus-stack --etcd 127.0.0.1:32379 --meta-prefix full-stack/woodpecker --bucket milvus-bucket --root-path milvus/wp
status --check
node list
meta log list

status --check verifies Admin and etcd access for the current session. These connection checks establish reachability; use a workload and the relevant log/data checks to establish application progress and readability.

Use wpcli with the dashboards

Start from the symptom and the test’s time window. Use in-flight operations and writer runtime for slow writes, log progress and segment diagnosis for stalled progress, and metadata inspection when coordinator state needs examination.

The write-stall, read-stall and data-corruption guides explain the evidence and verification needed for each investigation. Begin with their read-only inspection steps and choose any repair from the observed cause and consequences.
